# 从需求到上线

SpecDev 是一个领域入口，按当前任务引导到具体 Work；每项 Work 都可以独立使用。发版记录帮助任务跨会话延续；不把模型的推理和执行拆成必须逐项提交的表单。

## 一次正常发版

**收集与澄清。** 从 issues、用户对话、反馈、代码问题等收集来源，区分原话、已知事实和推断。只追问会改变范围、体验或代价的问题。已说清楚的需求不再重新访谈。

**先看必要的 UI。** 交互不确定时，用已有技术栈做能打开的原型，让用户确定主要体验。纯后端修改可以跳过。把仍在探索的候选与已确认设计分清；确认后保留原型本体或其可复现版本。

**形成 spec。** 将已确认范围、行为、设计引用和验收条件写进发版记录。复杂设计才另拆文件。Spec 是已知内容的综合，不是复制原始需求、重新生成 DESIGN、再向用户要求一轮格式批准。

**实施与验证。** 小任务直接做；较大任务拆成可独立实现和验证的结果。一个小清单通常够用，只有并行责任或上下文真的分离时才创建票据。目标跨度大时使用 goal-plan 整理里程碑，独立交付有价值时使用 tickets 拆分。使用当前宿主正常能力，无固定角色、执行引擎、领票、DAG 或循环调度。

**部署。** 已有环境就读取对应方法和当前状态；首次部署明确环境、入口、配置引用及数据影响。执行已授权动作后，检查实际部署版本、服务健康和关键路径。没有部署目标的库或本地工具，可以在用户要求的 PR、包或构建产物处结束。

**提纯与归档。** 把下一次还会用的原因、事实、设计或故障知识放回其长期维护位置。发版记录保留实际结果、未交付内容和相关版本，再归档为历史。

## 人在哪里参与

人主要决定产品需求和关键 UI 体验。需求明确之后，模型自行整理 spec、切片、实施和审查。用户可以在 Prompt 中进一步规定发布、验收、协作或质量要求。

授权与验收是两件事。用户说“可以开发”或“部署到 staging”授权相应动作；如果另有“最终页面由我验收”的明确要求，技术验证完成后仍保留待用户验收，不把部署成功变成验收通过。没有人工验收要求的任务自主完成，不主动加一轮审批。

相同目标、动作和范围的授权可以继续使用。环境事实变化、操作范围扩大，或仍缺少实际操作授权时，在准备好可审查结果后再确认。环境笔记负责保存事实，不能自行变成永久授权。

## 最少保存什么

默认数据根是 `.agents/speculo/.speculo/`，以下位置均相对该目录。安装器不预建它们。

| 内容 | 默认位置 | 何时需要 |
| --- | --- | --- |
| 一次交付记录 | `releases/<name>/README.md` | 跨会话、跨文件或需要保存交付结果 |
| 可选切片/附件 | 同一 release 目录 | 单文件已经影响恢复和协作 |
| 长效决定 | `knowledge/adr/` | 不解释原因会让后来者重复争论的重要取舍 |
| 当前背景 | `knowledge/context/` | 代码、配置、现有文档没有表达的有效事实 |
| 故障经验 | `knowledge/error/` | 根因和修复已验证，且值得避免重犯 |
| 当前设计 | `knowledge/design/` | 后续实现仍然需要参照的体验与资料 |
| 环境方法 | `environments/<target>.md` | 已经确定且会复用的部署目标 |
| 历史交付 | `archive/<name>/` | 工作结束或取消、当前事实已提纯之后 |

四类知识是本项目约定，不是行业强制标准。一个主题已有权威位置时直接更新它，不为了分类再复制一份。只有真实内容才建文件；不要求每次发版凑齐四类知识。

小修改的 PR 或提交说明可能已足够。源代码、测试、脚本和配置已经能回答的问题，不再改写成一份容易过期的文档。

## 一份记录可以这样小

以下只是说明，不是必填模板或可被 validator 判定完成的格式：

```markdown
# v0.6：任务详情面板

目标：点击任务后在当前页面侧边查看和编辑，保留列表位置。
来源：issue #12；11 月 6 日用户反馈。
设计：项目相对路径 ui/task-detail.stories.tsx，批准的提交 abc123。
范围：打开、编辑、关闭；不改任务存储。

- [x] 列表接入详情面板；单测和实际点击检查通过。
- [ ] 最终桌面端表现待用户验收（用户明确要求）。

验证：构建 abc123；相关测试命令及结果；页面对照截图链接。
当前结果：实现验证完成，尚未完成用户要求的验收。
下一步：提供该构建的桌面端页面供用户确认。
```

不要求另建 status.json、tickets-map、goal-plan 文件、验收 schema 或 TASK/REPORT。goal-plan 和 tickets 仍是可独立使用的方法，按任务需要把结果写入已有记录或拆出的材料。恢复上下文时读这个记录和其中相关引用；一次短问答甚至不需要这份记录。

## 设计是长期资料

设计可以是 HTML/CSS、React/Vue 组件、Storybook stories、设计 tokens、图片及必要说明。项目已有设计或组件目录优先。不要为了流程把它们再翻译成一份 change 内的 DESIGN。

当前设计会继续演进，因此每次发版记录都要引用本次采用的具体提交、不可变版本或清楚标识的快照。历史 release 中“批准过什么”不能被后来改动的当前文件悄悄替换。

验收实际涉及的页面、状态和主要区域：导航是否存在、详情出现在哪里、信息层级是否保留。可接受的数据差异、平台字体差异与业务适配要说明依据；不能因为功能仍在，就自行把已批准布局解释成示意。未批准的结构差异仍是未完成项。

这是对 [#105](https://github.com/NAMEWTA/Speculo/issues/105) 的语义处理：设计本体保留、实施直接引用、实际对照。没有字符串检查器可以证明 UI 符合设计。

## 部署环境记一次，之后复用

环境记录只保存会改变操作的事实：目标标识、应用和数据位置、现有发布入口、配置或密钥的引用位置、必要的数据变更顺序、健康检查、回退/恢复方法，以及最近实际核验的版本和时间。

优先链接项目已有 CI、脚本、Compose、Kubernetes 或 IaC 文件。不要把实际凭据复制进笔记，也不要为了记录创建一套 JSON 节点目录。

例如用户后续说“部署到 staging”，模型可以读取已有记录，确认当前版本与环境没有冲突后执行。涉及数据库变化时，确认备份、兼容顺序和可恢复性；普通静态页面发布不必模拟数据库流程。

部署回执写入本次 release：目标、构建/提交、实际动作、健康结果和未解决事项。发布命令退出 0 不是完整上线证据；观察不到目标时应明确标记未验证。

## 归档与提纯

发版目录移动到 `archive/<name>/` 后保留原名。内部附件可继续相对引用；跨目录设计和代码引用使用明确的项目相对定位或固定提交。移动时检查本次变更影响的链接，已有同名归档时保留双方，避免覆盖。

归档保存当时发生的事实；当前知识反映现在有效的事实。ADR 被替代时保留原决策理由并链接新决定；context、error、design 则更新其当前维护位置，历史可由 Git 和 release 引用追溯。

取消或部分交付也可以归档，但必须按实际结果记录，不把待验收、失败或延期写成已完成。对 [#106](https://github.com/NAMEWTA/Speculo/issues/106)，只有用户明确接受同范围延期/豁免时才能记录相应决定；没有回应不等于同意。

大段日志、试验截图和推理过程放在临时位置即可。只有解释结论、复现错误或满足明确交付要求的证据才长期保存。

## 查找对应方法

软件交付各环节以及环境连接、盘点、主机治理的具体入口见 [SpecDev 指南](workflows/specdev.md)。学习、媒体与论证使用各自领域的 Work，保留相应专业资料；不套用软件发版的全部步骤。
