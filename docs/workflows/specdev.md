# SpecDev：从需求到上线

SpecDev 的领域入口串联开发和运维。21 个 Work 各有具体任务方法，可以单独调用，也可以在一次已授权交付中连续使用。入口见 [SpecDev SKILL](../../template/workflows/specdev/SKILL.md)，完整列表见 [能力总览](../capabilities.md)。

## 从模糊需求开始

`triage` 处理 issue、反馈、讨论等原始来源，去重、辨认诉求并确定影响。`grill-with-docs` 补足会影响范围或体验的决定；它应先查代码与已有材料，集中追问真正缺少的信息。`wayfinder` 面向尚不清楚边界的大需求，用调查、假设与证据缩小问题。

例如“把当前工具改成可多人协作的服务”可能同时涉及身份、数据归属、离线和部署。先调查这些真实分歧，再确定一个可交付范围；不必先写完全部故事、票据和状态文件。

首次进入陌生项目时，`init-setup` 了解项目约定与实际命令。它不重建已有工具链，也不自动创建空知识库。

## 先确定体验，再形成规格

交互存在主要不确定性时使用 `prototype`。保留逻辑、关键状态、主要页面结构和可查看产物，优先沿用已有组件与技术栈。设计参考和可运行样例按问题选取，不把某种视觉样式套用到所有产品。

已确认的设计保存于长期位置，允许代码、组件、HTML、样式或图像。`spec` 引用本次采用版本，整理可见行为、接口或数据变化与完成条件。纯后端工作或已有清楚设计时，可以直接写规格。

## 规划与实现

`goal-plan` 用于跨多个结果或交付周期的目标、范围、里程碑与依赖判断。`tickets` 在独立开发、交付或验证有实际价值时拆分切片。简单任务直接实现；大任务中的票据也只需要足够说明目标、边界、依赖和完成条件。

规划不指定 Lead、Worker、执行引擎、派单消息、任务 DAG 格式或循环状态。用户可在 Prompt 中指定协作方式，当前宿主承担实际执行。

`implement` 根据规格和代码完成修改与相关验证。`diagnose-bugs` 通过复现、观测、假设排除和回归证据定位缺陷。`learn` 面向代码、系统或技术材料作有针对性的解释，保持与实际源代码或文档的联系。

## 两种审查与真实交付

`code-review` 检查变更正确性、回归和维护影响；`review-architecture` 检查职责、边界、依赖、数据流和方案取舍。架构审查的结论应能对应到具体问题和可验证改善，而非为了分层而增加模块。

`delivery` 完成当前请求覆盖的 PR、合并、版本或发布工作，并读回真实结果。技术检查、UI 对照和用户明确要求的最终验收分别记录，不能互相代填。

## 环境与部署

原 Ops 的五项能力合入同一领域：

| Work | 作用 |
| --- | --- |
| `environment-setup` | 确认控制端工具、访问方式和已有环境约定 |
| `server-connect` | 识别目标、建立或核验连接、保存可复用连接事实 |
| `inventory-view` | 只读盘点已知环境、节点、服务和最近观测 |
| `host-manage` | 在授权范围内维护主机与共享服务，验证影响和恢复路径 |
| `project-deploy` | 构建/发布既定版本，处理实际数据影响，检查目标健康 |

已有环境记录能让后续“部署到 staging”定位同一目标；记录不代替新的具体请求。读取已有 CI、脚本、Compose 或 IaC，避免把其内容复制进一套节点 JSON。

应用代码上传、进程运行和关键业务可用是不同观测。无法检查实际目标时，明确报告已做部分与缺失证据。数据迁移按实际兼容性安排，静态站点无需虚构数据库步骤。

## 接续、复盘与提纯

一份交付记录通常可串联来源、范围、设计版本、spec、已完成与剩余工作。上下文中断前更新这份记录；恢复后核对 Git、文件和实际系统状态。

`retro` 从真实过程找值得改变的方法和经验，避免凭想象总结事故原因。`archive-and-consolidate` 把当前有效的 ADR/context/error/design 更新回长期位置，再保存本次交付历史。当前设计与环境方法持续维护，历史不会覆盖它们。

持久化位置、批准设计与验收语义、归档引用见 [完整交付流程](../workflow.md)。
