# 通用文件、目录与命名

## 具体而非泛化

名称表达领域和职责。避免把不相关能力收纳进：

```text
utils helpers common misc shared manager processor handler
```

这些词并非绝对禁止；只有当 scope 真实单一且项目赋予明确语义时才可使用。无法给文件或类型起具体名称通常意味着职责尚未拆清。

## 局部一致性

- 目录、文件、类型、函数和测试命名遵循对应语言与框架；
- 同一 scope 内一致性优先于跨语言表面统一；
- 生成器和框架要求的特殊文件名保留；
- 重命名 public API、序列化字段或数据库对象前检查兼容影响；
- 大小写敏感性、Windows/macOS 文件系统差异纳入验证。

## 文件职责与大小预算

文件大小是 review 触发器，不是机械裁决。为不同语言和文件类型分别推导预算：

1. 统计当前可编辑文件分布；
2. 排除生成文件和 Vendor；
3. 区分生产代码、测试、配置、脚本和声明；
4. 结合复杂度、依赖数和修改频率；
5. 对存量超限文件使用 Ratchet。

超限时检查是否可以分离解析、验证、I/O、领域规则、状态编排、视图或平台适配。不得为了行数创建更模糊的文件。

## 目录层级

增加目录必须至少带来一项价值：

- 稳定边界；
- 独立所有权或发布；
- 明显降低导航成本；
- 框架/构建工具要求；
- 权限或依赖方向可验证。

“一文件一同名目录”不是通用默认。组件、package、module、crate 等具体布局完全由适配器和项目事实决定。

## 验证

项目规范应记录：

- 命名工具或 lint；
- 大小/复杂度的软预算与 Ratchet；
- 例外文件及理由；
- 跨平台大小写检查；
- review 时如何判断职责混合。
