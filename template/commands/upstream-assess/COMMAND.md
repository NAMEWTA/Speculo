# 上游评估

从 Git 和项目说明确认产品分支、上游仓库及范围。多个上游或产品分支无法消歧时只询问这个决定。用实际 SHA 固定产品 tip、观测上游 tip、共同基点和可以从历史证明的已集成版本。

## 取得证据

默认使用本地 refs；用户要求最新上游时刷新已确认 remote，并记录成功或失败及实际 tip。纯只读预览保持项目文件和 refs 不变。fetch 或镜像更新不等于已集成，不能推进集成检查点。

比较实际 diff，读取项目需要保留的定制行为与长期约束。找不到唯一 merge-base、历史不足或已有检查点不在实际历史时说明具体边界，不猜测一条“安全”合并线。

需要合并模拟时在隔离的临时位置操作，不改当前工作区、index 和分支。注意自定义 merge driver 或 hooks 会执行额外代码；未实际运行的检查保留为缺口。

## 判断影响

分别说明文本冲突、自动合并后的语义风险、定制行为冲突和本地未提交修改的重叠。零文本冲突不能证明功能兼容；重要判断对应到具体提交、路径和可验证行为。

给出建议集成范围、需要保留的定制、验证重点和固定 SHA 的复核方式。评估请求完成到评估；后续合并、提交或推送由用户的实际请求覆盖，不从参考文档推导授权。

## 记录与接续

需要保存时按 [持久化](../../references/memory.md) 复用已有交付记录；稳定的定制背景与本次观察的 SHA/冲突分别说明。只有产品历史和真实验证已证明集成，才把记录更新为已集成状态。

报告没有获取到的资料、失败的刷新和未执行的验证，避免把本地缓存或候选合并称为当前远端事实。
