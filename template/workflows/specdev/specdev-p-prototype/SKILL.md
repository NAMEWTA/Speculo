# UI 与逻辑原型

先明确原型要关闭哪个不确定性：交互与信息结构、视觉方向、规则、状态机、算法或接口可行性。UI 不清楚时优先原型，再把确认的行为写进规格；纯逻辑试验不要求设计文档。

## 定位项目与设计事实

读取相关页面、组件、tokens、样式、路由、截图和用户参考。技术栈名称不能证明现有视觉风格；已有被认可的结构和组件优先复用。新项目明确没有现成基线。

把核心用户任务、主要对象、关键状态与输入设备作为设计依据。不同参考有冲突时，说明采用哪一部分及理由，不把多个产品的导航与装饰全部堆在一起。

需要选布局、视觉组合或现成可运行样例时，打开 [设计资料入口](design-library/INDEX.md)，按问题选择参考；不默认全读。候选应在真实结构或交互上有区别，数量服从用户需要，不设统一配额。

## 做出可操作的 UI

使用项目组件、独立 HTML、组件 stories 或适合本项目的形式。呈现真实长度与密度的数据，覆盖本次关键的正常、空、加载、错误、权限或恢复状态；按钮要能展示其预期效果，模拟数据明确标注。

对照目标设备检查导航、内容区域、信息层级、滚动、弹层、键盘与焦点。实际浏览器可用时运行并观察，截图标明页面与状态；工具不可用时说明检查边界，不能把静态代码阅读称为视觉验收。

展示候选、推荐和取舍，让用户决定影响体验的部分。沿用已有明确认可，不重复索取同一确认；新的重大结构变化应明确提出。原型通过不等于生产页面或真实 API 已通过。

## 长期设计与版本

设计源直接维护在项目已有长期位置；没有时使用项目根 `.agents/speculo/.speculo/knowledge/design/<topic>/`。HTML、TSX、stories、CSS、tokens、图像和必要说明都可成为设计资产，不要求 change 内再写一份 DESIGN。

候选与当前已确认版本通过文件名、入口说明或注释区分。交付记录引用本次采用的固定提交、不可变版本或必要的小型快照，保留实际认可的来源；未来更新不覆盖这次验收依据。

## DESIGN 逐节引用原型

已确认原型的实际 UI、CSS 和 JS 是视觉与交互的直接证据。DESIGN 用于定位这些证据、解释设计意图及记录边界；不能用文字转述重新定义已由原型表达的效果。

编写或更新 DESIGN（或项目已有的设计说明）时，读取 [原型证据与引用方法](references/design-evidence.md)。每个涉及布局、样式、组件、状态、交互、响应式或无障碍的部分，都必须在该部分就近引用对应的原型文件与具体定位，并关联本次采用的固定版本。不能只在文首放一个原型入口，也不能用截图替代适用的 CSS/JS 源码引用。

静态部分无需编造 JS；未由原型体现的要求明确标为待补证据，纯背景说明标明来源与不适用原因。涉及实现效果但尚无证据的部分，先补原型或记录未决范围，不能写成已确认设计。引用格式及已有源码的完整示例见 [DESIGN 引用示例](references/design-evidence-example.md)。

向规格、任务、实施与审查传递同一组版本、章节和源码定位。实施前打开实际来源，完成后按同页面、状态、视口和主题对照；引用可访问不等于效果一致。原型或需求变化时同步更新受影响的设计引用与检查，保留原验收版本。文字与原型冲突时回到来源及用户最新明确决定处理，不能静默任选一种实现。

交付前逐节核对引用确实支撑该处描述、页面状态可以复现，缺失来源和未验证行为如实保留。已认可的导航、区域组合和信息层级不能在实施时自行降格为“只是 demo”；未获接受的偏差保持为未完成项。

## 逻辑试验

需要验证规则、算法、数据或状态行为时读 [逻辑原型](references/logic-prototypes.md)，用最小可运行试验比较输入与观察结果，覆盖能推翻方案的边界。代码与输出可以直接成为规格证据，注明模拟部分和未测风险。

交付可打开或运行的源、实际检查、已确认方向与未决项。需求或体验已足够清楚时继续 [Spec](../specdev-s-spec/SKILL.md)；已有明确规格和实施请求时可直接继续实现。
