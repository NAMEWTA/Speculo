# DESIGN 与原型证据

编写或更新 UI 设计说明，以及从设计转入规格、实施或审查时使用。沿用项目已有 DESIGN、设计章节或组件文档的位置；不要求每次交付另建一份文件，也不适用于没有 UI 的纯逻辑试验。

## 以已确认的原型为依据

原型呈现的 UI、结构源码、CSS 和 JS 共同说明界面如何布局、呈现和响应操作。DESIGN 负责让实施者准确找到它们，补充意图、业务约束、适用条件和未决项，不建立另一套凭形容词解释的视觉规范。

采用的是本次已确认的版本，不是目录中看起来最新的候选。记录固定提交、不可变版本或可核对的小型快照，连同页面入口、资源依赖和必要运行方式；每个章节的引用必须能归属到这个版本。同一版本可以在文首定义一次，再由各节明确引用；只有 `main`、`latest`、活动预览 URL 或本机绝对路径不足以复现。

用户新的明确决定可以改变设计。先说明与既有原型的差异，同步更新受影响原型、说明和版本引用，再实施该变化；尚未体现或验证的部分保留为未决项。发现原型缺陷、业务约束冲突或无障碍问题时明确处理，不能把“源码是依据”解释为必须复制已知缺陷，也不能只改 DESIGN 就宣称新的效果已经获认可。

## 每个部分引用什么

每个设计部分都在正文附近给出可打开的文件链接和能检索到的具体位置；文首总索引不能代替逐节引用。章节包含多个独立组件或行为时，分别定位，避免一个宽泛链接覆盖整页。

| 设计部分 | 必须定位的适用证据 |
| --- | --- |
| 页面、导航、区域与信息层级 | HTML 节点、组件、story 或路由及其区域标识；CSS 的布局、尺寸、滚动和层级规则 |
| 字体、颜色、间距、圆角、边框、图标和图像 | 实际使用这些样式的节点；CSS token、选择器、状态覆盖及素材文件，包含影响结果的字体或图标来源 |
| 控件与正常、空、加载、禁用、错误等状态 | 节点或组件的状态入口；相应 CSS；驱动状态的 JS/TS、fixture、story 参数或属性 |
| 点击、输入、切换、弹层、异步反馈与恢复 | 触发控件、事件处理或函数、状态变换和可观察结果；涉及过渡效果时补 CSS |
| 响应式、主题与动效 | 对应区域；断点、媒体查询、主题覆盖、过渡或动画定义；由脚本驱动时补 JS |
| 键盘、焦点、语义与无障碍 | HTML/组件的语义与属性、焦点样式及相关事件；依赖浏览器原生行为时指明元素和复现操作 |
| 背景、取舍、约束与例外 | 来源决定及所影响的原型部分；不对应可见效果时明确“不适用”及原因 |

CSS/JS 不要求拆成独立文件。单文件 HTML 的 `<style>`、`<script>`，组件内样式与处理器也可以定位。静态颜色说明可以写“JS 不适用：无状态变化”；不能给有交互的章节笼统标成不适用。

截图、录屏和运行观察补充说明实际呈现，标注页面、状态、视口、主题与版本；它们不替代可用的源码。只有图像参考而没有代码时，明确当前证据能力，不能伪造选择器、事件或运行结论。

## 让定位足够精确

引用由“版本 + 文件 + 具体位置 + 场景”组成。优先使用已有稳定的 DOM id、`data-*`、组件/story 导出名、CSS 选择器/token、函数或事件绑定。行号可以辅助，不能单独依赖可变分支的行号。一个选择器在多处出现时补充父节点、主题、媒体查询或条件分支。

分别核对各文件中的真实标识，不用“同名选择器”或“对应处理器”代替定位；HTML 的 id、CSS class 和 JS 查询条件可能不同，必须指向实际存在且生效的规则。

说明链接相对 DESIGN 所在目录还是项目根；仓库固定提交链接可直接打开。`file.html#panel` 只有在真实 HTML id 存在时才是页面锚点，不能把 CSS 选择器或 JS 函数名伪装成可跳转的 URL fragment。可点击文件链接后以代码字体写出检索位置即可。

每节可以用一行、列表或小表表达，不要求统一表单。例如：

```markdown
### 任务详情

原型依据：版本 P1；[任务页](../prototype/tasks.html) 的 `#task-detail`；
[样式](../prototype/ui.css) 的 `.task-detail` 和窄屏媒体查询；
[交互](../prototype/ui.js) 的 `openTaskDetail`、关闭事件与焦点返回。
复现场景：任务列表 → 打开详情 → 关闭，沿用原型中该状态的视口与主题。
意图与边界：保留列表上下文；真实 API 接入不得改变已确认的位置和交互。
```

上面是语法示意，文件和标识必须替换为真实来源，不能原样当成证据。参见 [已有原型的完整引用示例](design-evidence-example.md)；它使用本库真实的 HTML/CSS/JS 定位。

## 写作、修改与交付

1. 打开本次采用的原型及其依赖，确认版本、页面和状态。先读或运行事实，再写设计说明；不要从旧文档反推代码“应该”长什么样。
2. 逐节建立上述引用，再补写目的、约束和必要边界。复用实际 token、尺寸和事件，不把精确证据改写成“适当留白”“现代弹层”等可任意解释的要求。
3. 检查描述是否真的由来源支持。原型没有的加载、错误、权限、主题或移动端状态明确写为待补，不能由相近状态推断已经完成；需要本次实现的先补充对应证据或解决未决决定。
4. 把章节、源码定位和固定版本带入规格、Ticket 与实施上下文；直接实施也读取这些源码。不只向下游传递设计摘要或原型首页。
5. 实施后比较相同页面、状态、视口和主题的实际界面，检查布局、视觉、交互、焦点和恢复行为。允许适配框架或真实数据/API，但不能因此改变已确认的可见效果；合理差异说明依据，未接受的偏差保留为未完成项。

原型改动、目录移动、代码重命名或文档调整时，更新受影响引用并重新核对相应结论。共享 CSS/JS 改动还要检查引用该规则的其他章节；历史交付仍指向原采用版本。正文与原型冲突时先核对版本和用户决定，不用文档重写或换基线掩盖实现差异。

完成前检查：每节是否有适用的 UI/CSS/JS 证据或明确不适用原因，链接和标识能否定位到正确版本，状态能否按描述复现，以及检查是否真正执行。缺浏览器时可以核对源码和引用，但必须保留视觉与交互验证的限制；不新增依靠关键词或链接数量判定设计一致性的校验器。
