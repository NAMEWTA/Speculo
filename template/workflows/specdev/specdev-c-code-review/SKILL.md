# 代码审查

保留用户选择的审查范围：指定本地文件、单个 commit、两个端点的差异、分支相对共同祖先，或远程 PR。只读审查本身不授权修改代码、评论或合并；用户同时要求修复时再继续实施。

## 固定实际输入

PR 读取真实 base/head；单个 commit 比较它与指定父提交，多父提交先确定语义；分支基线与显式区间不要混用。记录所审版本与未提交变化，避免审查过程中悄悄换成最新 HEAD。

有效空差异如实说明，不虚构 findings，也不把未检查范围标为通过。本地文件审查不因缺少 Git 而要求初始化仓库。

读取差异以及受影响的调用方、测试、接口和相关规格。分别判断功能与工程风险、是否符合用户需求及设计；缺少规范时说明能检查和不能判断的部分，不伪造批准。

## 寻找真实缺陷

重点沿实际执行路径检查行为、边界条件、状态与资源生命周期、失败恢复和回归。权限与信任边界、并发、迁移、公共接口或依赖变化时展开 [审查风险](references/review-risks.md)。

涉及 UI 时直接比较已确认设计与实际实现的页面结构和关键状态。导航丢失、信息层级改变或旧布局回流，需要具体依据；不要通过修改设计记录消除实现偏差。未实际渲染就说明视觉检查的限制。

将确定问题、需要验证的疑点与个人偏好区分。每个有效 finding 指明位置、触发条件、实际后果、证据和修复方向；严重程度由影响决定，避免用笼统“可能有风险”充数。

## 交付

优先呈现最值得修复的问题，给出覆盖范围、实际验证及剩余不确定性。没有发现时直说没有发现，不宣称代码绝对无缺陷。

用户要求独立审查时使用实际独立审查者；普通审查不强制额外角色或协议。来源、代码或配置变化后重新评估受影响结论，旧版本通过不自动覆盖新版本。

通常在会话或原 PR 中返回；需要接续的结果写入现有交付记录，长报告才单独保存。无需 CR 编号、固定两轴模板或文档格式校验器。
