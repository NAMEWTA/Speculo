# 有实际影响时展开的审查视角

这些是发现问题的方向，不是每次必须填写的表。沿当前变更的真实入口、调用方和数据检查。

| 变化 | 核心问题 |
|---|---|
| 公共接口、CLI 或 SDK | 参数和返回兼容吗？错误是否可判断？消费者、文档和示例是否同步？ |
| 状态与持久化 | 谁拥有状态？写入失败、重启、并发或部分提交后还能恢复吗？ |
| 数据迁移 | 原数据是否保留？迁移是否会重复执行？新旧程序是否存在并行窗口？ |
| 权限与输入 | 授权发生在实际效果之前吗？路径、注入、越权、跨租户及敏感输出有哪些可达路径？ |
| 异步与资源 | 取消、超时、子进程退出和订阅释放是否完整？迟到结果会污染新状态吗？ |
| 外部依赖 | 版本和行为假设有依据吗？失败、限流、重复调用与结果未知怎样处理？ |
| UI | 已确认结构、关键状态、键盘与实际交互是否落实？测试是否只覆盖外观或局部组件？ |
| 测试与配置 | 删除测试是否失去真实风险覆盖？默认值、工作目录与平台行为是否有不同？ |
| 文档与技能 | 事实与实际代码相符吗？触发条件会误用吗？有无失效链接、误删能力或互相矛盾指令？ |
| 性能 | 真实工作量下是否出现额外 I/O、全量扫描、重复计算或无界资源？有测量而非猜测吗？ |

报告问题时说明能触发它的条件与可观察后果，连接具体代码证据。不能证明的怀疑作为待验证项，不混进确定缺陷。

用户要求的覆盖范围不能因为“精简”而遗漏；高风险并不意味着输出更长，而是沿真实失败路径查得更深入。
