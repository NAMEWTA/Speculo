# 目标计划与接续

把用户的目标变成能实际推进的工作清单，明确交付终点与真实依赖。没有规划需要的小任务直接执行；本入口不引入固定角色、调度器、派单协议或循环计划文件。

## 制定计划

读取已有需求、规格、设计、当前代码和实际交付状态。确认此次终点是方案、实现、PR、发布还是部署，保留用户明确的数量、范围和时间约束。

按可观察的结果列出工作，说明必要顺序、重要风险和最终怎样判断整体完成。每项只写执行需要的背景与完成条件；已有票据直接引用，不再复制其状态。

需要几个发布阶段时，说明每阶段交付的价值、前置条件和集成检查。需要独立协作时写清责任边界与共享修改点；由当前宿主和用户选择执行方式，不维护另一套团队编排。

## 执行、恢复与调整

用户要求实施或继续时，复用同范围已有授权，核对 Git、实际文件、测试和部署状态，从尚未完成的工作继续。只请求计划时交付可执行计划，不把文档中的建议当作新的操作请求。

新事实改变范围、依赖或可行性时，更新受影响的清单，说明调整原因及哪些原检查已失效。保留已完成成果与仍有效的决定，不因为重规划而重跑无关工作。

遇到阻塞先尝试取得能改变判断的证据；没有新信息时不重复相同尝试。记录阻塞的具体原因、已发生的变化和可继续的下一步，继续不受影响的已授权工作。

## 整体完成

逐项回读实际结果，再检查跨模块集成和用户原始目标。任务列表勾完不能替代产品路径、用户明确要求的验收或目标环境检查；未完成项直接说明影响。

计划通常放在同一 release 记录内。上下文中断前更新进度、阻塞与下一步即可，无需 goal-plan/tickets-map/implementation-map 的多层镜像。
