# 项目部署与运行验证

定位用户指定的项目、环境、服务器与实例，读取已有发布脚本、基础设施配置、环境文档和本次实际版本。已有目标和同范围授权直接复用；目标含糊或记录与现场不符时先消歧。

## 准备真实部署

从当前源码、构建配置和依赖了解真实启动方式、配置来源、持久化位置、迁移、健康检查和恢复能力。固定本次提交或产物，不以生成通用 Compose 代替完成项目部署。

查清依赖属于项目专用、共享服务还是外部托管。共享数据库、Redis、对象存储等保留真实账号、逻辑资源与消费者关系；主机级代理和网络入口分别记录。未知产品按实际资料核对，不猜适配参数。

沿项目既有布局放置应用、数据、日志、备份与版本产物。代码发布目录与持久数据分离，确认容器挂载或服务配置指向正确位置。必要细节参见 [环境与运维](../references/operations.md)。

## 数据与执行顺序

部署涉及数据变化时，核对备份、迁移兼容性、执行责任和恢复方法是否实际可用。无数据影响的改动不增加虚构迁移步骤；代码回退也不意味着数据库可以无损回退。

有依赖时先准备并验证 provider，再配置逻辑资源和消费者，最后切换实际入口。跨主机部分成功要逐目标保留事实，不声称一次操作具备全局事务。

按当前授权执行构建、上传、部署、迁移与切换。超时先查询实际状态，再恢复或补做，避免重复迁移或发布。失败时保留现场与已发生变化，执行适用恢复；无法继续时说明影响和恢复入口。

## 验证与长期记录

检查目标上的实际版本、服务状态、关键请求或用户路径，以及适用的数据读写结果。命令退出成功、端口存活和业务可用分别记录；没有实际执行的检查明确标出。

更新现有 release 记录中的目标、版本、时间、迁移与实际结果。只把后续部署仍有价值的命令、路径、依赖和恢复变化写回环境说明；服务端已有维护文档时同步必要事实。

升级、迁移和回退都以本次明确目标与现状为依据。停止或卸载服务时保留数据、账号与共享依赖，除非用户明确要求相应删除。

交付真实位置、版本与验证结果。环境记录应足以支持下一次“部署到这里”，无需再交付一套 SpecDev/Ops 交接材料。
