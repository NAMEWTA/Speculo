# 红灯反馈回路

本文件只负责阶段 1–2。回路尚未满足完成门时，不加载假设或修复材料。

## 构建顺序

按大致顺序穷尽适用方式：

1. 能触及 bug 的失败测试；
2. 针对开发服务器的 curl/HTTP 脚本；
3. 固定输入的 CLI 调用和已知良好输出 diff；
4. 对 DOM、控制台或网络断言的无头浏览器脚本；
5. 回放真实请求、负载、事件或追踪捕获物；
6. 启动最小系统子集的一次性夹具；
7. 属性或模糊测试循环；
8. 可供 `git bisect run` 使用的状态检查夹具；
9. 旧/新版本或配置的差分循环；
10. 最后手段：复制并定制 `<Path>{roots.workflows}/specdev/D-diagnose-bugs/scripts/hitl-loop.template.sh</Path>`。

## 收紧

把回路当作需要优化的产品：缩小启动范围和测试目标；断言精确症状而非“没有崩溃”；固定时间、随机、文件系统与网络。记录一次运行耗时和复现率。

非确定性问题以提高复现率为目标：批量运行、并行、增加压力、缩小时间窗口或注入 sleep，直到失败率稳定到可调试区间。

## 最小化

看见正确红灯后，逐项删除输入、调用者、配置、数据和步骤，每次只删除一项并重跑。删除后仍红则永久移除；变绿则恢复。完成时剩余每一项都承载故障。

## 无法建立回路

停止并列出尝试过的方式，请求以下之一：可复现环境、HAR/日志/core dump/带时间戳录屏等捕获物，或临时生产插桩授权。没有红灯不得进入假设。

## 完成门

- 命令已至少运行一次并保存调用与输出；
- 驱动真实 bug 路径并断言用户精确症状；
- 结果确定，或有稳定且足够高的复现率；
- 秒级或已证明是当前最短可行回路；
- Agent 可无人值守运行，或由结构化 HITL 脚本捕获结果；
- 最小复现的每个剩余元素都有负载作用。
