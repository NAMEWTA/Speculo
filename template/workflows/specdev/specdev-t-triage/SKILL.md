# 需求收集与评估

先判断当前意图：浏览队列、保存原始反馈，或评估准备实施的具体需求。浏览和收集不必创建版本交付，更不自动关闭 issue。

## 收集原始需求

读取用户指定的 issue、PR、对话、反馈、截图和现有代码。保留来源链接、关键原文与必要上下文，区分原始请求、后续澄清和自己的归纳。遇到重复需求链接共同问题，同时保留独有约束。

浏览队列时说明覆盖的项目、时间、筛选和分页范围。资料尚未完整时不要把“没找到”写成“不存在”。需要长期收集且项目没有待办入口时，可在交付记录之外维护一份简短的 inbox 文档；只有实际进入交付的项再链接对应 release。

## 评估是否值得做、怎样算解决

围绕用户、问题、现状和目标行为核实：是否已实现，是否重复，是否符合项目方向，影响哪些已有功能、数据与使用者，解决它需要什么证据和投入。

- Bug：取得复现、错误输出或可靠事件证据，区分症状与原因；未知原因交 [故障诊断](../specdev-d-diagnose-bugs/SKILL.md)。
- 新需求：补足主要场景、异常和完成条件，说明收益、代价、已有替代及范围。
- PR：固定实际 base/head，读取差异和相关检查，判断它已经满足什么、还有什么缺口。

优先级依据影响、紧迫性、证据强度、依赖和工作量，而不是标签或用户表达强度。暂缓、需要信息、重复、已经解决与明确拒绝分别说明理由；没有依据就保留未知。

## 保存与接续

将进入交付的来源、判断、范围、验收想法和未决问题写入现有 release 记录。无需额外 source/triage 状态文件。远程标签、评论、关闭等动作按用户授权执行并读回；本地分析不依赖远程写入成功。

边界未知时进入 [需求探索](../specdev-w-wayfinder/SKILL.md)，关键取舍待定时进入 [决策访谈](../specdev-g-grill-with-docs/SKILL.md)，体验不明确时先 [原型](../specdev-p-prototype/SKILL.md)，足够清楚则形成 [Spec](../specdev-s-spec/SKILL.md)。已请求实施且范围明确的小修复可直接继续。

交付应让下一位执行者知道原请求、已核实事实、建议及其理由、完成条件和下一步；评估通过不等于实现已经完成。
