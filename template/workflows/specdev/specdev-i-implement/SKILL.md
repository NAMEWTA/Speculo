# 实施与验证

从当前请求或已有规格开始，读取受影响入口、调用方、测试、设计和重要项目决定。任务已经清晰时直接实施，不强制补建 Ticket、Goal 或阶段状态文件。

## 形成正确改动

确认当前工作区与已有修改，保留无关用户编辑。沿项目习惯修改真实源文件，复用已有组件、接口和工具；删除或替换能力时说明实际承接，不能把“简化”理解成少交付。

涉及关键模块边界时先比较几种实际可行设计，选择能把复杂性集中在清晰接口内的方案。普通局部修改不要求写设计对比。领域词汇、公开接口和持久数据变化按已确认规格保持一致。

Bug 修复先取得可靠失败证据；能运行回归测试时观察原问题，再验证修复。测试围绕行为和失败风险选择，避免镜像实现的低价值断言；文字或低影响配置修正按实际影响检查即可。

同时更新受影响消费者、示例、配置和必要文档。移除旧测试前明确原风险仍由何处覆盖，或说明对应行为已经退出。新工具、模型上下文和返回格式要从真实调用入口验证。

## UI 与真实使用路径

动手前沿 DESIGN、规格或 Ticket 的 [原型证据引用](../specdev-p-prototype/references/design-evidence.md)，打开本次确认版本的相关 HTML/组件、CSS 与 JS，核对页面结构、视觉值和状态转换；不能只读文字概述后凭印象重画。引用失效、源码缺失或文字与原型矛盾时，明确受影响范围并补齐依据，继续不受影响的工作。

优先复用原型中适用的结构、tokens、样式和交互；框架迁移或真实 API 接入可以调整工程实现，但要保持已确认的可见结果。按同一页面、状态、视口与主题比较实际页面。复用组件不意味着可以沿用已经被替代的旧导航或布局；未获接受的差异仍是未完成项，不能靠改写设计说明或替换基线消除。

原型截图不证明生产页面已经实现。实际检查键盘、焦点、空/错/加载状态及本次受影响的关键交互，保留必要截图或观察；缺浏览器或后端时写清未验证范围。

## 检查与收尾

运行能验证本次行为和回归风险的检查，读真实结果并修复发现的问题。高风险接口、权限、并发、数据迁移等按 [可靠性参考](../references/reliability.md) 展开；是否独立审查由真实风险与用户要求决定，不固定审查团队。

任务明确要求最终用户验收时，技术检查、原型认可与发版许可均不能代替其实际决定。延期只按用户对同一范围的明确反馈记录。

更新现有记录的结果、验证和剩余事项；遇到阻塞保留可恢复现场，继续独立已授权部分。请求包含 PR、发布或部署时，继续 [开发交付](../specdev-d-delivery/SKILL.md) 或 [项目部署](../specdev-d-project-deploy/SKILL.md)，不在第一版实现后提前结束。
