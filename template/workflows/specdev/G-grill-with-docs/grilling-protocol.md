# 设计访谈协议

目标是关闭会影响产品行为、架构边界、风险或验收的关键决策，不是把所有可能问题都问一遍。

## 1. 开始前先发现事实

先读取代码、配置、测试、现有 Spec、ADR、CONTEXT 和 LOG。可从环境获得的事实不得转交给用户回答；只有偏好、风险承受度、业务取舍或互斥目标需要用户决策。

## 2. 决策树

按风险和信息缺口覆盖，不机械提问：

1. 用户问题与成功状态；
2. 参与者、权限与主要流程；
3. 范围边界和明确非目标；
4. 状态、数据、不变量与失败模式；
5. 接口、兼容、迁移和发布；
6. 安全、隐私、性能、可观测性；
7. 验收与验证接缝。

## 3. 每轮只关闭一个关键决定

每轮格式：

1. **已知事实：** 简短说明当前共识和证据；
2. **唯一问题：** 不使用复合问题；
3. **可行选项：** 只列实质不同的方案；
4. **权衡：** 对范围、体验、架构、风险和未来成本的影响；
5. **推荐：** 明确给出默认建议及原因；
6. **用户结论：** confirmed / deferred / rejected；
7. **落盘：** 更新 LOG，并按需要更新 ADR 或 CONTEXT。

## 4. 记录规则

- 所有已确认或显式延后的决策写入 `<Path>{roots.state}/specdev/changes/{change}/LOG.md</Path>`；
- 长期架构决策追加到 `<Path>{roots.state}/specdev/changes/{change}/ADR.md</Path>`；
- 稳定领域知识追加或合并到 `<Path>{roots.state}/specdev/changes/{change}/CONTEXT.md</Path>`；
- 不因追求“文档完整”而复制同一事实；工件冲突按 `<Path>{roots.workflows}/specdev/common/rules/artifact-contract.md</Path>` 裁决。

## 5. 停止条件

- 关键决策已关闭，足以进入 Spec；或
- 用户明确延后，且该延后不会伪装成 Ready；或
- 缺少外部信息，change 标 blocked；或
- 继续提问只会产生低影响实现细节，应交给 Ticket 或实现阶段决定。
