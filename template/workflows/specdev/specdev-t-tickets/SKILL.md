# 实施切片与 Tickets

先判断是否需要独立票据。一次可完成的改动在现有记录中列小清单即可；用户要求拆票、内容过大或协作需要时，再创建可独立阅读的 Ticket。

## 从行为切分

读取规格、采用的设计版本、关键接口与现有测试，按可验证的用户结果拆分。优先让一块工作贯穿所需界面、服务、数据和检查，不按“先所有后端、再所有前端”机械切割。

准备性重构只有确实降低实施风险时单列，并明确它支撑哪个结果。数据或公共接口迁移可按扩展、迁移、收缩安排必要顺序；不是所有任务都需要这三阶段。

每块说明目标、相关背景与来源、预计修改范围、完成条件和真实依赖。涉及 UI 时保留同一已确认版本中负责页面/状态的 [原型证据引用](../specdev-p-prototype/references/design-evidence.md)，包括适用的结构、样式与交互源码定位；引用 DESIGN 时保留相关章节及其直接源码链接，不把它们压缩成一句视觉描述。涉及数据时说明迁移与恢复责任。只有确实需要的技术约束写入票中，不复制全项目规范。

## 支持独立协作

检查是否存在未覆盖的规格、重复责任、循环依赖和共享修改点。接口两端、数据模型、配置、生产调用方与文档的变化应有明确承接；可并行的判断来自这些事实。

准备独立上下文时，提供足够的来源路径、当前事实、预期结果与验证入口。无需固定 TASK/REPORT、角色名称、执行工具或每票创建工作区。

用户指定交付数量或拆分粒度时保留；确有冲突说明原因，不静默少交付。新的未知会改变产品行为时先澄清，局部工程细节可留给实施者。

## 交付与继续

用现有 release 记录维护简短顺序与链接，各票只负责自己的细节；状态和结果尽量写在原条目，避免 Map、Goal 与 Evidence 多处同步。

展示每块带来的结果、依赖与风险。已有完整实施请求时直接接续 [实施](../specdev-i-implement/SKILL.md)；只要求规划时返回可用票据。整体验收仍检查原规格和跨块集成，不能由所有票“完成”自动推导。
