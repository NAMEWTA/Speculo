# 环境、共享依赖与数据运维

供环境接入、主机维护、部署与盘点按实际需要读取。普通 Markdown、现有脚本与基础设施代码即可描述环境，不规定注册 schema 或统一执行器。

## 环境的最少有用信息

能够回答：这是哪个目标；怎样连接；项目、应用和数据在哪里；怎样发布；怎样确认运行正确；失败后怎样恢复。已有 Terraform、Compose、服务配置或运行手册能回答的内容直接引用。

一台主机可以运行多个项目，一个项目也可以部署到多个环境。记录真实关系和作用范围，区分本机控制端、目标主机、共享服务、外部 provider 与应用实例。

连接别名不等于经过验证的身份。记录观察时间与权限边界；地址、账号或数据根变化时核对目标，不能让同名环境悄悄换机器。

## 布局与依赖

代码与发布产物尽量可替换，持久数据、备份和运行配置保持明确位置。沿项目已有布局组织，不强制统一目录；容器 volume、宿主路径与应用真实数据参数要能对应。

共享数据库、缓存、对象存储等记录逻辑资源、账号、网络与消费者，不把公共服务物理数据复制进每个应用目录。项目副本是否共享数据由真实需求决定，不能按实例数推断。

先验证 provider，再准备逻辑资源与权限，再部署消费者。跨 Compose 文件或跨主机依赖需要实际顺序与健康条件，不能用无效的 depends_on 关系代替。

## 迁移、切换与恢复

查清数据规模、可接受停机、兼容窗口、写入来源和迁移单一执行位置。备份需要可用的恢复方法；仅生成备份文件不证明能恢复。

数据库结构变化、数据复制与应用版本切换分别考虑。涉及持续写入时说明增量追平、验证和切换条件，避免只复制一次后假设一致。代码版本可回退不代表数据格式可逆。

每个目标分别记录已发生效果，尤其关注连接中断和命令超时。先核对实际服务、版本和数据再重试，恢复可能是继续完成、切回入口或补偿，而非一律重新执行。

## 验证

检查进程/容器、日志、版本、配置与关键业务路径，必要时使用隔离测试数据验证读写并清理。检查范围与权限来自当前任务，不为了验证增加不必要生产写入。

观测成功、未测、过期和失败分别说明。健康接口成功不能覆盖未验证的数据迁移或依赖连通性；只监听端口也不证明业务可用。

## 记录与秘密

环境文档保存部署和恢复入口及事实；执行细节留在本次交付记录或日志，不复制所有输出。服务端已有 README 时同步必要变更，避免多份配置真值。

只引用凭据位置，日志和报告脱敏。停止或移除应用不默认删除数据、共享服务、网络和账号；资源清理先辨明归属与实际依赖。
