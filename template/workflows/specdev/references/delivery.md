# 交付、CI 与发布操作

供开发交付 Work 按当前操作读取；项目已有发布配置与用户授权决定实际流程。

## PR 与来源处理

固定本次远程仓库、目标分支与 head，确认推送的是预期改动。保留未提交或他人修改，合并冲突按实际两边意图解决，不能为了消除冲突直接覆盖一侧。

PR 描述解释问题、行为变化和实际验证。用户要求把本地任务投影为 issue 时，先查已存在条目，链接共同规格与对应范围，重试前先对账，避免重复创建。

关闭来源 issue 前确认其需求确实被交付；包含其他未完成范围时说明剩余内容。新需求、澄清与开发结论应能区分，不用修改原始请求来配合实现。

## CI 与告警

查看当前提交对应的检查，区分排队、执行中、跳过、失败和成功。环境缺失不等于代码失败，也不等于已经通过；失败先读真实日志并取得可解释的原因。

安全告警核对受影响版本、实际使用、可达性与修复方式。改依赖或权限时验证项目功能，不能通过关闭检查、扩大凭据能力或删除断言让 CI 变绿。

仅重跑失败或被修改影响的检查。存在必需独立审查或发布 gate 时遵守真实项目约定，同一范围已经给出的授权继续有效。

## 发布预检

从项目代码识别版本来源、changelog、构建物、包文件、许可、安装入口、registry 和 release 配置。通过实际安装或消费场景核对产物，尤其注意被忽略文件、缺少模板和本地相对路径。

核对目标上是否已有同名 tag、暂存发布或公开版本。确认本次产物与提交一致；签名、供应链证明、平台确认和 2FA 按实际项目要求处理，不发明通用批准仪式。

## 多目标发布与恢复

按依赖顺序执行获准动作，并分别记录 tag、registry、GitHub Release 等实际结果。暂存成功、公开可下载和用户环境可用不是同一状态。

遇到超时先查询服务端记录；已有不可变版本不要重复上传。部分目标完成时保留事实，在原记录继续剩余步骤，不以整体失败描述掩盖已发生的发布。

恢复方案必须适合当前产物与数据。撤销公告、回滚部署、替代包版本和删除资源有不同效果，依据用户范围与平台能力选择；无法恢复时给出明确影响与接续入口。

## 交付记录

记录能定位成果的提交、PR/issue、版本、产物和真实检查，必要时保留失败与恢复位置。无需独立 DEL、publish、delivery、PR 多层账本；一次交付记录可链接真实远程来源。
