# 开发文档的归属与验证

SpecDev 中新增、审查、压缩、迁移工程文档或用户可见说明时读取。只规定开发工件的归属和验收，不复制全局写作能力。代码注释继续由 <Path>{roots.workflows}/specdev/common/rules/code-commenting-rule.md</Path> 拥有；工件冲突按 <Path>{roots.workflows}/specdev/common/rules/artifact-contract.md</Path> 裁决。

## 一个事实一个负责位置

Work 入口说明何时及如何执行；common 说明跨 Work 判断；项目代码、接口说明和 README 描述当前行为；change ADR 记录本次已接受决定及真实取舍；LOG 保存讨论、未确认和被替代解释；Evidence 保存实际执行。永久知识仅经 A 原网关晋升，archive 是历史，不作为当前行为默认权威。

先定位读者任务、本文职责和适用细节层次。教程按前置知识与步骤通向结果；参考按可搜索主题定义当前行为。下级模块的细节放在其 owner，父级只说明职责并链接。产品事实不在多个 Work 复制；必要的局部权限、失败与安全条件不能因为“去重”变得不可见。

## 编辑时保留完整语义

改写前核对主体、动作、条件、顺序、必须/可以/禁止、例外、副作用、owner、失败和后果。较短不自动较好。去掉代码复述、装饰和只有原会话能理解的“上面第几项”“稍后那张 PR”等叙述；有长期价值的理由保留在 ADR，不能连同条件一起删掉。数字和来源没有核实就写未验证，不编造备选方案或测试经历。

使用精确术语：HTTP API、服务、进程边界和事务边界有实际含义时应保留，不机械替换成 module/seam。当前文档用当前事实；规划保留在上游合同，已实现总结必须与代码/测试/Evidence 相符。固定历史版本和事故时间线保留在其历史 owner。

## 事实核对与派生内容

先改真实源，再运行项目现有生成器。命令、示例、默认值、错误和平台差异以当前代码和实际执行核对；没有密钥/运行环境时明确检查到哪一层，不能沿用邻近文档的说法。类型片段、导出路径、链接、配置和生成 freshness 分别使用项目真实检查。

目标项目已有双语约定时，最小同步受影响语义、结构、术语和代码，核对 counterpart；没有该约定不创建双语三件套。哈希配对不证明翻译正确，结构通过也不证明事实正确。

外部可感知破坏在引入它的同一改动维护项目已有升级说明：影响对象、旧新行为、必要步骤、成功确认、不可回退部分和已知限制。保留已发布数据的兼容义务；不要把预发布产品等同于数据可丢弃。不是所有内部重构都需要升级指南。

## 可见文字也是行为

工具描述、prompt、参数、诊断、CLI/UI 文字的改变按其真实消费者验证。纯说明可使用链接、示例和类型检查；模型或用户行为受影响时补相应行为证据。没有该层运行能力则报告缺口并按原 Gate 保持未通过，不能打着“文档任务”绕过。

验收回读修改源和派生物，列出检查、未验证项及明确的新增行为。不用字数变化宣称 Token 或费用节省。
