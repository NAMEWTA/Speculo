# 编写规格

规格串联已经讨论过的来源与设计，让实施者知道应交付什么及如何验证。先读取现有需求、用户决定、相关代码与测试；缺少与本次无关的工件不构成阻塞。

## 明确行为与范围

解释谁遇到什么问题、当前行为是什么、本次改变什么，以及哪些事项暂缓。对主要场景写出触发条件、可观察行为和结果；接口、数据结构、权限、兼容性及性能等内容只在实际影响交付时展开。

对于 UI，将每项行为要求连接到本次确认的原型版本、页面与状态，并保留对应 HTML/组件锚点、CSS token/选择器/媒体查询、JS 事件与状态转换等适用的源码定位，按 [原型证据引用](../specdev-p-prototype/references/design-evidence.md) 组织。只有原型首页或 DESIGN 文档入口不足以定位具体行为。

已有 DESIGN 时引用对应章节及其原型证据；编写设计说明时，各节就近指明所依据的源码，文字补充目的与取舍，不能覆盖已确认的 UI、样式和交互。原型已表达清楚的内容直接引用，不再复制成 change 内 DESIGN。尚无原型证据的要求标明缺口或设计决定，不写成已验证事实；纯后端不要求 UI 资料。

工程细节保持可调整空间。确实要固定的接口或约束说明理由；不要锁定无必要的逐文件实现步骤。新设计取舍超出已有共识时聚焦解决，广泛未决问题使用 [决策访谈](../specdev-g-grill-with-docs/SKILL.md)。

## 让完成条件可以判断

为重要结果找实际验证入口，例如产品页面、公共 API/CLI、集成事件或稳定单元接缝。说明怎样触发、应观察到什么，沿用项目已有测试和检查方式；不为了形式把每条要求都编号或规定测试层级。

涉及写入或异步工作时，说明失败、部分成功、超时未知、重试、取消和恢复对用户可见的含义。接口或持久化变化明确兼容、迁移和恢复限制。只有实际需要时才展开 [可靠性与验证](../references/reliability.md)。

区分已确认事实、可逆假设和阻塞决定。高影响缺口不能藏在笼统“按最佳实践处理”中；局部默认值可明确说明并在实现中验证。

## 一个权威位置

通常把规格放在 release 记录内。用户明确需要独立 spec、篇幅较大或多人引用更方便时拆成 `spec.md`，原记录改为链接，避免双份规范。

规格至少足以解释目标、范围、关键行为、重要约束与实际完成条件；按内容组织，不使用强制模板或 JSON schema。来源、设计和重要决定能回读即可。

范围清楚且已有实施请求时直接进入 [实施](../specdev-i-implement/SKILL.md)。只有任务规模或协作需要才 [拆票](../specdev-t-tickets/SKILL.md)；交付目标复杂时可使用 [目标计划](../specdev-p-goal-plan/SKILL.md)。
