# 工程与 Agent 情境检查

只在主题涉及工程实现、Agent、外部工具或系统运行时使用；由共享探究规则的调用方按需读取。下面是教学情境，不代表用户系统已经存在这些故障。

## 工程主题的条件性检查

先画清模型提出调用、编排器调度、客户端发送、服务端产生效果、结果回写的责任边界。将观察到的现象与可能原因分开，不根据一条日志就确定根因。按主题选择相关情境，不要求每次全讲。

| 情境 | 应暴露的假设 | 要推进到的判断与验证 |
| --- | --- | --- |
| 同一工具重复调用 | 同名工具多次等于死循环 | 区分合法分页、轮询、独立业务意图和重复执行；观察游标、任务状态与证据增量，定位模型、编排器、客户端或服务端的责任 |
| 不同工具往返 | 工具名不同就代表任务有进展 | 检查语义相同的业务意图、状态循环和无进展轨迹；定义总体步数、时间、费用预算与停止、转交规则，不只提高上限 |
| 问询工具反复询问 | 用户没有回答是唯一原因 | 检查答案是否进入状态、上下文遗漏、恢复重放和真正缺失字段；复用已答信息，但不能以避免追问为理由假定高风险授权 |
| 写工具超时 | 没收到成功等于没执行成功 | 区分明确失败与结果未知；核对业务状态、操作标识、服务端幂等合同、并发请求和参数变化；测试业务完成后响应丢失的恢复 |
| 服务错误或限流 | 所有错误都适合重试 | 依据实际 API 合同区分输入、权限、限流、暂时故障与结果未知；说明重试责任层、总预算、退避与抖动、降级和人工交接 |
| 多层重试 | 每层都重试更可靠 | 检查模型、编排器、SDK、队列是否叠加尝试；测量总请求量和恢复时间，防止重试放大与持续过载 |
| 部分成功或进程重启 | 从上一步重新执行总是安全 | 定位业务效果与完成记录之间的窗口；区分查询、恢复、补偿与重新执行，讨论不可逆效果；测试恢复重放和重复投递 |
| 工具结果可解析但不可信 | 合法 JSON 等于业务正确且可信 | 检查业务不变量、过期结果、权限、敏感日志与工具结果中的恶意指令；验证信任边界而非服从返回文本 |

每个选中的主要问题至少说清：现象、候选机制、区分它们的证据、负责处理的层、方案及边界、测试输入和可观察的通过条件。用受控故障与反例检查误报：正常分页不能判为死循环；两个合法相同参数操作不能被错误合并；未执行的故障实验不能写成已验证。

进一步追问应来自方案暴露的新条件，例如幂等标识的有效期、并发冲突、重启后识别、恢复时权限变化、结果核对不可用和日志脱敏。答案仅有“加重试、加熔断、加监控”时尚未形成完整解释。不要承诺仅修改提示词就能保证 exactly-once 或生产可靠性。
