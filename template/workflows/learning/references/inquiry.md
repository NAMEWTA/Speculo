# 从表面问题探究机制

在用户要深入理解、查明失败机制、阅读复杂源码或把知识用于真实情境时使用。选择当前问题需要的深度，不把每个概念都扩展为系统设计审计。

## 探究主线

从实际问题或一个可观察的反常现象出发，找出原判断依赖的假设。追踪输入经过哪些组件、规则或状态到达结果，寻找能够区分解释的证据或反例。再讨论处理方法、代价和验证方式。

这是一组思考工具，可来回使用，不是必须填满的章节。信息已经充分就直接解释；缺少的事实会改变结论时，优先查资料、源码或运行小实验，必要时再问用户。

有用的问题包括：

- 什么条件下成立？改变哪一个条件会失败？
- 是谁持有状态和决定权？边界另一侧看到了什么？
- 观察结果能排除哪些解释，仍不能排除哪些？
- 局部正确为什么可能造成整体错误？成本由谁承担？
- 修复作用在哪一层？怎样证明它恢复了目标行为？

## 工程问题的深入示例

| 表面现象 | 值得展开的机制 | 区分解释的证据 |
| --- | --- | --- |
| 同一工具被调用很多次 | 正常分页或轮询、重复输入、缺乏进度记忆、终止条件无效 | 参数变化、游标、返回结果、目标完成度；调用次数本身不足以判定循环 |
| 工具名称一直变化 | 多步依赖可能正常，也可能只是换一种方式重复同一动作 | 每一步是否产生可复用的新信息、更新状态或缩小未知 |
| 用户“已经说过” | 原话是否存在、当前上下文是否可见、摘要是否丢失约束、解释是否歧义 | 原始消息、当前输入、持久化记录；不能先归咎用户没有回答 |
| 写操作超时 | 服务端未执行、仍执行中、已提交但响应丢失 | 服务端状态、操作标识、结果查询；超时不自动等于可以安全重试 |
| 多层重试拖垮服务 | 单层退避看似合理，叠加后放大请求和延迟 | 每层次数与截止时间、请求链路、整体负载与失败率 |
| 重启后部分结果重复 | 已完成与待完成动作没有可靠区分、外部副作用不可回滚 | 实际产物、幂等键、事务边界、恢复路径；不能只重跑整个计划 |
| 输出符合 JSON 格式却不正确 | 结构有效与事实、权限、业务规则、语义正确是不同层 | 来源、引用完整性、业务约束、下游实际行为 |
| 模型答得合理但系统失效 | 任务缺少必要状态，或责任层错置 | 模型输入、工具协议、宿主恢复、客户端与服务端各自的职责 |

这些例子用于理解机制，不要求所有学习任务引入调度器、审查器或复杂持久化。普通学科也可以用反例、因果链与边界条件深入探究。

## 处理未知与分歧

区分已证实事实、合理解释、待验证猜想和价值选择。不同来源冲突时比较对象、版本、时间、方法与适用条件；无法裁决就保留分歧，提出最能减少不确定性的下一项调查。

一次实验只支持它覆盖的情境。解释“为什么”时避免仅复述现象；推荐处理办法时交代其作用点、失败边界和验证方法。不要通过堆叠术语、列出更多风险或无证据的确定语气来表现深度。

## 形成可复用理解

将结论写成用户可以重新运用的模型：在什么条件下，会发生什么，为什么，怎样识别，如何应对。附实际来源或案例；失效条件同样保留。

学习者自己回答时保留原答和反馈。模型代为研究时只声称完成了研究，不能替用户认领理解或掌握。新的证据改变模型时更新同一笔记，原始观察仍可追溯。
