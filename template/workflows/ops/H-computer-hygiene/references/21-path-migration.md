# 持久化路径归一化：执行与回滚方案

## 目标布局

建议只针对用户自己管理的开发环境采用下述逻辑布局。Windows 的默认 DevRoot 是 `%LOCALAPPDATA%\Dev`；macOS 是 `~/Developer/.tooling`；Linux 是 `~/.local/share/dev`。用户可以指定其他绝对路径，脚本只生成方案，不写入配置或创建新 SDK。

```text
DevRoot/
  data/     # runtimes、受管工具、包含持久状态的数据
  cache/    # 每个工具独立子目录；可重建不代表可以无条件删除
  config/   # 仅支持迁移的配置；保留必要的官方配置锚点
  bin/      # 必要且明确归属的可执行入口/官方 shims
  tmp/      # 明确归属的临时工作区域，不替代全部系统临时目录
```

“统一”是一个清晰的权威来源和可理解的目录规则，不是所有文件强行放同一盘。系统/安装器路径不动；pnpm、编译、权限和卷特性要求不同盘时，用同样的组织规则并登记例外。Windows 原生、WSL、容器、x64、arm64 分别规划，不混用 SDK 或二进制缓存。

## 第一步：冻结证据与保全

记录每个工具当前 PATH 命中、实际版本、管理器/安装来源、项目 pin、配置优先级、持久变量以及 IDE/CI 使用者。静态扫描不能证明生效时，补可信原生查询或保留未知。包含源码、credentials、用户工具和本地未发布依赖的目录逐项识别。

在本机私密目录备份配置原文件、权限、环境变量原值和类型，并保存清单与校验值。不要导出完整环境或把私有仓库凭据复制到报告。区分“配置备份”“可重新下载的缓存”和“唯一数据备份”；后者必须有实际可读的副本，不能只保存路径列表。

关闭 IDE、daemon、构建、安装器和相关工具。记录验证项目和离线需求。迁移期间不运行清理，避免源/目标状态同时变化。

## 第二步：决定主管理器与单一配置来源

优先保留现有工作正常、来源清楚的主管理器。mise/asdf 只是候选统一层，不在未核验平台/插件支持时替换所有工具；rustup 和 uv 可以分别管理它们擅长的内容。不要为了“看起来统一”额外叠加管理器。

确定 PATH 的维护入口，避免系统变量、用户变量、shell profile、管理器初始化、IDE 和 `go env -w` 多处互相覆盖。保留项目级版本 pin、wrapper、lockfile。官方 shims 可以存在；不要用新的手工符号链接/目录联接掩盖未解决的旧配置。

## 第三步：按数据类型选择迁移方法

| 类型 | 推荐方法 | 不能默认做的事 |
| --- | --- | --- |
| 纯缓存 | 让工具在新配置路径重建，验证后再确认旧缓存清理 | 把移动缓存当成永久空间回收 |
| Maven local repository | 先保全本地 install 产物；合并配置后验证 | 删除整个 `.m2`、覆盖 settings 中认证/镜像 |
| 管理器安装的 JDK/Node/Go | 采用受支持的重新安装/迁移方法，保留版本 pin | 直接剪切含绝对路径的安装树后修改 PATH |
| Cargo/Rustup Home | 保全工具、配置、凭据、override；按官方支持迁移 | 只搬 registry 却丢失 bin/credentials，或清空全部 Home |
| Python/uv 工具/项目 venv | 从已保全依赖重建，检查 editable/本地包 | 假设 venv 任意位置均可直接搬动 |
| 全局 Node/Go/Cargo 工具 | 精确列明工具身份、版本、来源，按新入口重装/修复 | 把 bin 当缓存、盲拷 shell shim 或原生扩展 |
| 系统/安装器管理路径 | 使用官方修改安装或重装流程 | 手改注册表/收据或移动 Program Files/Homebrew 安装树 |

工具行为与变量来源按 [20-toolchains.md](20-toolchains.md) 和 [00-sources.md](00-sources.md) 核验。

## 第四步：先会话测试，再持久化

先在独立终端中调整某一个生态的会话环境，验证路径解析和最小工作负载。不要一次改所有语言。通过后备份并修改唯一的持久化入口；采用可重复应用的定点修改，不往 profile 反复追加同一块配置，不覆盖其他程序维护的 PATH。

Windows 分别处理用户和机器环境、REG_SZ/REG_EXPAND_SZ 及原始顺序，不用 `setx PATH` 拼接全量覆盖。macOS 分别验证登录 shell、交互 shell和 GUI/IDE，不假设 `.zshrc` 能配置所有进程。任何需要启动新进程才能生效的更改均标明；当前终端结果不能替代新会话验证。

## 第五步：验收矩阵

JDK/Maven：解析正确，IDE 和 wrapper 使用预期 JDK，代表项目可构建，本地未发布依赖仍可用。Node/pnpm：版本/prefix/store 正确，既有全局工具和代表项目正常，锁文件没有未经批准变化。Go：SDK、模块/构建缓存、GOBIN、toolchain 指令与代表测试一致。Rust：rustup default/override/targets、cargo 安装工具和项目可用。uv/Python：解释器、项目 venv、tool 入口、editable 依赖及锁文件正常。

网络下载、包脚本执行、构建 hook 和测试副作用需要在验证前说明。验证只涵盖被测范围；没有逐项目检查时不能声称全机兼容。新终端、重启后的 IDE 和相关后台任务分别验收。

## 第六步：回滚与退出旧目录

配置层失败时恢复备份的原值、类型、权限和解析顺序，重新开启终端。SDK/虚拟环境安装失败时保留原安装和旧环境，恢复主用入口。隔离缓存可用 receipt 恢复，但源目录已被重建时不能覆盖，必须人工处理。

只有在验证完成、唯一数据已保全、旧入口不再被任何已知项目/任务使用，并且用户明确批准后，才把旧目录转入独立清理计划。保留期由用户选择，不硬编码“过 N 天自动删除”。永久清理没有本脚本自动回滚保证。

报告为每个生态记录迁移前/后、改动文件、确认 ID、验证结果、例外和回滚位置；失败或未执行写清楚，不把建议映射画成既成事实。
