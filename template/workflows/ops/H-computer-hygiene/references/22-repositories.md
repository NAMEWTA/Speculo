# 仓库、构建产物与“安装不规范”识别

## 不以路径名判定可删

仓库克隆在 Downloads、Desktop、临时目录、某个 SDK 旁边，可以标记为组织结构待审查，不因此认定是垃圾。Cargo 的 Git checkout、Go module cache、包管理器下载的源码也可能是正常管理行为；先识别所有者和用途，不能见到 `.git` 就把它称为非法仓库。

默认只扫描用户明确授权的项目根，不遍历整个 Home 或磁盘。目录标记、多个 Node lockfile 和构建产物名称是线索，不证明重复、无主、未使用或可删除。Git 命令默认不运行，防止未知仓库配置、过滤器、fsmonitor 或工具链产生副作用。

## 仓库保全清单

| 问题 | 需要的证据 | 未完成时的结论 |
| --- | --- | --- |
| 是否有未提交/未跟踪/忽略但重要的文件 | 可信仓库的状态、文件所有者说明、构建/数据用途 | 保留整个工作区 |
| 是否有未推送提交、其他分支或 stash | 分支/上游、各相关 refs、stash；不能只看当前分支 | 不删除 `.git` 或仓库 |
| 是否关联 worktree / submodule | gitfile 指针、实际关联关系与本机支持的原生清理 | 不把 `.git` 文件认作损坏或残留 |
| 是否有 LFS、本地依赖或未发布包 | 对象与远端可用性、离线需求、Maven/Cargo/Go 本地状态 | 保留并备份唯一对象 |
| 看似重复的克隆是否真的可替代 | 远端身份、各分支/提交、工作区内容、项目配置 | 同名/同远端不是重复证明 |
| build/dist/target 是否可重建 | 生成规则、版本控制、源码目录和项目所有者确认 | 人工候选，不自动删除 |
| node_modules/.venv 是否仅依赖安装 | lockfile、editable/local path、原生扩展、离线要求 | 不自动删除或简单搬动 |

Git 状态、worktree 和 clean 的官方核验入口为 [GIT-1](00-sources.md#git-1)、[GIT-2](00-sources.md#git-2)、[GIT-3](00-sources.md#git-3)。读取 Git 状态前确认仓库与执行程序可信；配置过滤器等风险不能被“只是 git status”掩盖。

## 建议的整理方法

将个人源码统一到明确项目根，如 `~/Projects` 或自行选择的开发盘，按组织/项目分层。不要把源码放在可清理缓存根或由 SDK 卸载器管理的目录。不同 clone、worktree、fork 和实验副本保留唯一名称及用途说明。

迁移前保存 Git 和本地依赖证据，确定 IDE workspace、任务、脚本、路径依赖、虚拟环境和外部配置是否指向旧位置。移动仓库后重建不支持重定位的环境并验证，不直接删除旧路径来测试“有没有人还在用”。

项目工具通常优先 wrapper、项目 pin 和 lockfile，而不是用全局版本替代所有项目。一个项目出现多个 Node 包管理锁文件可提示团队确认管理器，但可能处于迁移期；不自动选最新或最小的那个，其余删掉。

不默认执行 `git clean -fdx`、`git gc --prune=now`、`git reset --hard` 或按相同远端批量删除克隆。即使先做 dry-run，预览也不是删除授权。不可复原的 Git 对象、未提交资料和忽略文件必须保全。

## 重复文件

默认脚本只列下载目录的安装包、压缩包及大文件元数据，没有计算全盘内容哈希。文件名、大小、修改时间相同只能产生待复核候选，不能证明重复。后续精确去重应独立授权读取范围，跳过云占位/链接，区分硬链接、克隆、备份语义和内容完全相同但用途不同的文件。即使哈希相同，也需选择保留位置并检查引用关系。
