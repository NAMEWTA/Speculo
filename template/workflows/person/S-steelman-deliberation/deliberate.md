# 回答前：双向钢人化协议

仅在当前 change 没有通过验证的 `steelman-dossier.md` 时读取本文件。完成本阶段后停止形成结论；后续裁决规则由 `judge.md` 拥有。

## 1. 重述真正要解决的问题

先区分并写清：

| 层次 | 必须回答的内容 |
|---|---|
| 表层问题 | 用户字面上问了什么 |
| 真正决策 | 用户最终需要选择、拒绝、排序或承诺什么 |
| 当前倾向 | 用户目前偏向哪一边；未表达时明确写“未表达” |
| 决策目标 | 真正优化的是收入、速度、品牌、自由、关系、学习、风险还是其他目标 |
| 时间尺度 | 短期与长期是否会产生不同答案 |
| 约束 | 预算、资源、期限、不可逆性和利益相关方 |
| 假设 | 哪些尚未验证的前提正在推动判断 |
| 成功标准 | 什么可观察结果代表问题被真正解决 |

重述必须通过可识别性检查：用户应当能说“对，这才是我真正想解决的问题”。可以补全结构，不得替用户偷换目标、价值观、事实或立场。

## 2. 分离事实、推断、价值与未知

把输入逐项归入：

- **已验证事实**：有材料、代码、测试、配置或可靠来源支持；
- **合理推断**：由事实推导，但仍可能被新证据推翻；
- **用户价值偏好**：只有用户能够决定的优化方向；
- **尚未验证假设**：当前影响结论但缺乏证据的前提。

不要把流畅叙事当证据，不要把用户的信心当证据。可外部发现且会影响结论的事实，先按 `evidence-gate.md` 探索。

## 3. 进行双向钢人化

钢人化不是替某一边宣传，而是先把对方会认可的最强可信版本补完整，再判断。

### 二元问题或已有明确倾向

分别形成：

1. **钢人 A：支持用户当前倾向的最强可信论证**；
2. **钢人 B：反对当前倾向、或支持最强替代方案的最强可信论证**。

每个钢人必须覆盖：

- 核心主张；
- 成立所需前提；
- 最强理由与证据；
- 最有利适用条件；
- 最好可能结果；
- 对方最难回答的质疑；
- 会使该论证失败的事实或阈值。

### 三个及以上真实候选方案

不要强行压成一个“支持”桶和一个“反对”桶。对每个可行选项使用稳定结构：

```markdown
### 选项 A：<名称>
#### 最强支持论证
...
#### 最强反对论证
...
#### 成立条件
...
#### 失败条件
...
```

每个选项都必须包含四个小节。只覆盖真实可行选项，不为了显得全面制造虚假选择。

### 四条硬约束

1. 强化的是**可信版本**，不得凭空创造事实、来源、概率或用户动机；
2. 两边采用相同证据标准，但不要求结论概率相等；
3. 一边在事实层面明显更弱时，明确写出，不制造虚假对等；
4. 论证必须保持可识别性和意图一致性，不能强化成原立场持有者都不认可的新立场。

## 4. 找出共同基础与真正分歧

分别列出：

- 双方共同接受的事实或目标；
- 真正冲突的事实判断、因果预测、风险容忍、时间尺度或价值排序；
- 只是措辞不同、实际上并不冲突的部分。

真正分歧必须能解释“为什么双方在看过彼此最强版本后仍得出不同结论”。

## 5. 找到会改变结论的关键变量

建立变量表：

| 变量 | 当前假设 | 哪个阈值会改变结论 | 当前不确定性 | 是否可外部发现 | 用户特异性 |
|---|---|---|---|---|---|

只保留真正可能翻转方案排序、风险判断或行动时机的变量。复杂问题可以有多个变量，但要识别其中最具决定性的一个。

## 6. 只选择一个关键问题

为候选问题按以下维度比较：

```text
决策影响 × 当前不确定性 × 用户特异性 × 用户可回答性
```

最终问题必须同时满足：

- 只关闭一个变量；
- 用户回答后可能改变结论；
- 只能由用户提供，或至少用户是该偏好的权威；
- 与当前处境、目标或约束绑定；
- 不是模型可通过代码、材料或公开资料查明的事实；
- 不是把多个问题用逗号、斜杠或连续问号伪装成一句。

如果用户输入已经明确回答该变量，仍把问题写入 dossier，并把对应原文作为已提供回答持久化；不要再次询问。

## 7. 回答前停止条件

生成 dossier 后：

- 不给出最终建议；
- 不排序方案；
- 不写“我更倾向”；
- 不提供下一步行动；
- 不用措辞暗示哪个钢人已经获胜。

唯一允许面向用户的下一动作，是原样提出那个关键问题并等待回答。
