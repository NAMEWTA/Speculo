# 注释、JSDoc 与文档

## 注释必须关注 WHY

这是固定默认原则。注释用于解释代码无法直接表达的原因和约束：

- 为什么必须采用此顺序。
- 为什么不能删除看似多余的逻辑。
- 平台、协议、性能或安全约束。
- 第三方缺陷和规避方案。
- 竞态条件和资源生命周期。
- 非直观产品规则。

不逐行翻译代码，不用注释补救模糊命名或过大模块。

## 风格

- 优先一行或短段落。
- 靠近被解释逻辑。
- 原因必须具体、可验证。
- 修改实现时同步更新。
- 看似特殊的兼容或性能逻辑应说明删除条件。

## 不应提交

- 注释掉的旧代码。
- 无跟踪信息的“以后优化”。
- 与实现重复的大篇教程。
- 无法验证的猜测。

## JSDoc

主要用于：

- 公共库 API。
- 插件和扩展点。
- 跨团队、跨包或跨进程契约。
- 参数有单位、边界或特殊格式。
- 函数有重要副作用、取消或异常语义。

内部显而易见函数不机械添加 JSDoc。

## TODO 与设计文档

TODO 必须符合项目确认的任务编号格式并说明删除条件，例如：

```ts
// TODO(PROJ-1423): Remove after all clients send protocol v3.
```

多方案权衡、迁移计划和长期架构放入 `docs/` 或 ADR；源码注释只保留理解当前实现所需的最小上下文。
