# 测试策略

## 单元测试靠近实现

这是固定默认原则：单元测试与源文件共置，便于发现、移动、重命名和维护。

```text
shell-command-quote.ts
shell-command-quote.test.ts
```

跨模块集成、契约和 E2E 测试集中管理，例如：

```text
tests/
├── integration/
├── contracts/
└── e2e/
```

生成项目规范时应根据现有框架确认实际后缀和目录，不机械复制示例。

## 测试命名

测试名描述可观察行为，不描述实现步骤。禁止 `it('works')` 和 `describe('utils')`。

## 覆盖范围

关键模块考虑：

- 正常路径。
- 边界和空输入。
- 无效输入。
- 错误传播。
- 取消和超时。
- 并发或重复调用。
- 资源清理。
- 已修复缺陷的回归场景。

## 缺陷修复

1. 添加稳定复现问题的失败测试。
2. 确认修复前失败。
3. 实施最小修复。
4. 确认回归和相关测试通过。
5. 必要时增加跨平台或集成测试。

## 确定性与 Mock

测试不依赖真实当前时间、外部不稳定网络、执行顺序、共享可变全局状态、本机特定路径或无种子随机数。

Mock 系统边界，不 Mock 被测模块每个内部调用。优先测试真实纯函数和可观察行为。

## 质量门禁

- 不得为使 CI 通过而删除或长期跳过失败测试。
- 新功能和缺陷修复必须按风险补充测试。
- 测试代码同样遵守清晰命名、资源清理和大小预算。
