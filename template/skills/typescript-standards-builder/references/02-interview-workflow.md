# 用户问答与决策收敛

## 总体原则

问答的目标是确认项目规则，而不是让用户重复描述仓库事实。

- 一次确认一个决策维度。
- 每个问题给出推荐默认值和理由。
- 选项必须具体可执行，不使用“严格一点”“灵活一点”等空泛描述。
- 用户回答后立即记录，不重复询问。
- 只问真正影响生成结果的内容。
- 固定默认原则不重复征求同意，除非存在硬冲突。

## 推荐提问顺序

### 1. 规范范围和遗留策略

仅在范围不明确时询问：

- 整个仓库。
- 指定应用或包。
- 新代码强制、旧代码 Ratchet。
- 全量迁移并设置阶段计划。

推荐：成熟项目采用“新代码强制、旧代码只降不升”。

### 2. 目录主轴

仅在仓库结构混乱或新项目中询问：

- 业务领域优先，运行环境作为第一层边界。
- 架构层优先。
- 包边界优先的 Monorepo。
- 保留现有结构，仅禁止继续扩散问题。

默认：先隔离运行环境，再在环境内部按业务领域组织；领域内部局部平铺。

### 3. React 文件命名

仅 React 项目且仓库没有统一事实时询问：

- `PascalCase.tsx` 业务组件，Hook 使用 `use-*.ts`。
- 全部 `kebab-case.tsx`。
- 保留生成器目录的特殊规则，业务代码使用统一规则。

### 4. 模块和公开 API

在导出方式不统一时询问：

- 默认命名导出；默认导出仅限框架入口。
- 保持现有默认导出惯例。
- Barrel 仅允许作为领域或包公共入口。
- 完全禁止 Barrel。

推荐：命名导出优先，Barrel 只用于稳定公共入口。

### 5. 类型建模

在项目没有明确偏好时询问：

- 默认 `type`，需要声明合并或扩展时使用 `interface`。
- 默认 `interface`，联合和工具类型使用 `type`。
- 完全遵循现有局部惯例。

同时确认外部输入验证使用已有 Schema 库，还是要求自定义守卫。不得为此擅自引入新依赖。

### 6. 文件大小预算

根据实际分布推荐阈值。可询问：

- 普通 `.ts`、`.tsx`、测试、脚本分别设置软上限。
- 仅设置“超限必须说明”的审查门槛。
- 先使用 Ratchet，不立即阻塞历史超限文件。

推荐基线可从 `.ts` 300、`.tsx` 400、测试 700、脚本 600 行开始，但必须根据项目分位数调整。

### 7. 测试与门禁

确认：

- 单元测试共置的文件后缀。
- 集成、契约和 E2E 的目录。
- PR 必跑的 `format:check`、`lint`、`typecheck`、`test`、`build`。
- 是否运行受影响测试还是全量测试。

固定默认：单元测试共置，缺陷修复需要回归测试，核心门禁不得被删除或跳过。

### 8. 例外和迁移

确认项目如何记录：

- Lint/类型例外说明格式。
- TODO 的任务编号格式。
- 临时例外的负责人和删除条件。
- 历史债务的 Ratchet 指标。

## 结束条件

当以下内容均已确定即可停止提问：

- 目录和命名规则可执行。
- 类型、安全和运行时验证边界明确。
- 文件大小与拆分策略明确。
- 测试位置、命名和门禁明确。
- 例外和遗留治理明确。
- 项目特有框架规则已覆盖。

不要为了填满问题数量继续提问。

## 决策摘要格式

```md
## 自动识别
- 包管理器：pnpm
- 模块系统：ESM
- 测试：Vitest，单元测试已共置

## 用户确认
- React 组件使用 PascalCase.tsx
- Barrel 仅用于包公共入口

## 默认基线
- 领域内部局部平铺
- 注释解释 WHY
- 普通 TS 文件软上限 300 行

## 兼容例外
- generated/ 保留生成器命名，不执行文件大小检查
```
