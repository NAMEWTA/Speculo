# 通用架构与依赖边界

## 目标

规范描述“边界为何存在、如何验证”，语言适配器再描述 package/module/crate 的具体实现。

## 模块职责

- 每个模块拥有可命名的业务或平台职责；
- 公开入口与内部实现分离；
- 依赖方向单向、可解释、可自动检查时应自动检查；
- 边界间通过显式数据/接口合同通信；
- 避免跨层深导入、共享可变全局状态和隐式副作用；
- 生成代码、基础设施代码和业务代码有明确所有权。

## 目录主轴

优先保留仓库已经稳定的主轴。新设计默认：

1. 先按独立部署、运行时或包边界分离；
2. 在边界内按业务领域或能力组织；
3. 领域内部局部平铺；
4. 只有出现稳定子域、独立生命周期或明显浏览负担时增加层级。

这不是强制所有语言采用相同目录。Java package、Go package、Rust crate 与 Vue/React feature 的语义不同。

## 公共 API

- public API 必须有稳定入口、兼容策略和测试；
- 内部实现不因便利而被公开；
- 跨模块只依赖对方公开合同；
- 破坏性变更需要迁移说明、版本策略或同步消费者；
- 序列化格式、数据库 schema、事件和 CLI 输出都属于 API。

## 循环依赖

识别源码、构建模块、运行时服务和数据层面的循环。修复优先：

1. 移动错误归属的能力；
2. 提取稳定合同；
3. 反转依赖；
4. 使用事件或适配器；
5. 最后才考虑共享模块。

`common`/`shared` 不应成为绕过边界的垃圾场。

## 验证

生成项目规范时给出仓库真实验证方式，例如：

- lint/import boundary rule；
- build module dependency；
- package visibility；
- architecture test；
- workspace/crate graph；
- code review checklist。

没有自动工具时，MUST 规则必须列出精确 review 路径。
