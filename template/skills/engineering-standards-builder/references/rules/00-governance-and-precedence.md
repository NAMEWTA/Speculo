# 治理、规则级别与冲突优先级

## 规则级别

生成项目规范时统一使用：

- **MUST**：正确性、安全、协议、公共 API、数据、资源生命周期或已生效门禁要求；必须有可执行检查或明确 review 条目。
- **SHOULD**：大多数场景适用；偏离时需要记录理由、scope 和恢复条件。
- **MAY**：允许的模式，不作为伪门禁。
- **EXCEPTION**：临时或永久例外；必须写明所有者、原因、范围、风险、到期或删除条件。

不要把偏好包装成 MUST。无法验证的规则最多为 SHOULD，并给出具体 review 证据。

## 冲突优先级

按以下顺序解决冲突：

1. 安全、协议、编译器、运行时、监管与数据正确性的硬约束；
2. 用户针对本项目明确确认的目标状态；
3. 当前生效的构建配置、CI 合同、发布合同与公共 API；
4. 当前模块稳定且占主导、能被证据证明的实践；
5. 对应语言、框架和工具的当前官方文档；
6. 团队选定的风格 profile；
7. Builder 默认建议。

较高优先级不等于静默覆盖。若目标状态与当前硬约束冲突，生成“当前状态 → 迁移阶段 → 目标状态”，而不是直接写一条无法落地的规则。

## 证据来源

每条重要规则标记一个或多个来源：

```text
repository-fact
user-decision
official-guidance
builder-baseline
compatibility-exception
```

`repository-fact` 必须附路径或命令证据。`official-guidance` 只作为适用默认，不能覆盖项目版本和真实配置。`builder-baseline` 不得伪装成项目既有事实。

## 不可被历史惯例弱化的底线

以下问题即使在仓库中普遍存在，也必须采用 Ratchet 或迁移方案，而不是继续扩散：

- 外部输入未经验证；
- 密钥、Token、密码或个人敏感数据泄露；
- 资源、线程、goroutine、任务、监听器、连接或子进程没有所有者和关闭路径；
- 错误被静默吞掉或只记录后继续假装成功；
- 公共边界使用无约束动态类型；
- 依赖方向绕过模块边界；
- 删除测试、关闭核心规则或放宽编译配置以隐藏失败。
