# 格式化、Lint 与复杂度

## 工具统一风格

格式由 Prettier、Oxfmt、Biome 或仓库选定工具自动完成。代码评审不讨论工具已能确定的空格、换行和引号偏好。

常见基线：

```json
{
  "singleQuote": true,
  "semi": false,
  "printWidth": 100,
  "trailingComma": "none"
}
```

具体值可不同，但必须全项目一致并在 CI 检查。

## 通用格式规则

- 2 空格缩进，除非仓库明确不同。
- 文件使用 LF 和末尾换行。
- 控制结构始终使用花括号。
- 不手工用空格对齐列。
- 避免将功能修改与全仓库格式化混在同一变更。
- 生成文件由生成器维护，不人工格式化修改。

## Lint 覆盖

### 正确性

- 未使用变量和导入。
- 浮动 Promise。
- 不可达代码、重复分支。
- React Hooks 规则。
- 意外赋值或错误比较。
- 无效正则和转义。

### TypeScript

- 显式 `any`。
- 类型导入一致性。
- 无意义断言。
- Switch 穷尽检查。
- `@ts-ignore`。
- 不安全成员访问和调用；在性能允许时启用类型感知规则。

### 架构与维护

- 循环依赖。
- 禁止跨层导入。
- 文件大小。
- 函数复杂度和嵌套。
- 重复导入。
- 无意义 Barrel。

## 禁用规则

禁用必须：

- 精确到单行或最小块。
- 指明规则名。
- 说明无法通过设计消除的原因。
- 有退出条件时附跟踪编号。

```ts
// eslint-disable-next-line no-await-in-loop -- Server requires ordered writes.
await sendBatch(batch)
```

禁止文件级关闭核心类型安全、Hooks 或 Promise 规则来掩盖问题。

## 文件大小预算

建议触发审查的阈值：

| 文件 | 软上限 |
|---|---:|
| 普通 `.ts` | 300 行 |
| React `.tsx` | 400 行 |
| 测试 | 600～800 行 |
| 构建/生成脚本 | 600 行 |
| 函数 | 40～60 行 |

行数不是唯一指标。还应考虑：

- 分支和圈复杂度。
- 依赖数量。
- 状态数量。
- 修改频率。
- 是否混合多个抽象层级。

## 拆分方向

- 解析与验证。
- 领域规则与 I/O。
- 状态定义与 Selector。
- UI 容器与展示组件。
- 平台无关逻辑与平台适配器。
- 公共契约与内部实现。

拆分后文件名必须具体，不得产生新的 `helpers.ts`。

## 遗留文件

对历史超限文件采用 Ratchet：不要求一次全部重写，但新修改不应继续扩大；每次触及时降低复杂度或提取一项明确职责。
