# 落地、例外与迁移

## 例外原则

规范允许例外，但不允许无记录的例外。例外必须：

1. 有具体技术原因。
2. 范围尽可能小。
3. 在代码、配置或 PR 中说明。
4. 不破坏核心安全与类型边界。
5. 临时例外有退出条件和跟踪任务。
6. 经代码评审确认。

## 例外示例

```ts
// eslint-disable-next-line @typescript-eslint/no-explicit-any
// Why: Vendor callback type is incorrect; remove after SDK-481 is fixed.
function normalizeVendorPayload(payload: any): NormalizedPayload {
  return vendorPayloadSchema.parse(payload)
}
```

该例外仍在边界进行运行时验证，不让 `any` 传播。

## 遗留项目迁移

不要一次性重写全部代码。推荐阶段：

### 阶段 1：建立事实和门禁

- 固定包管理器和锁文件。
- 增加稳定的 `format:check`、`lint`、`typecheck`、`test`、`build` 命令。
- CI 先报告问题，再逐步改为阻塞。

### 阶段 2：阻止新增债务

- 新文件遵守命名和大小规则。
- 新 API 不使用 `any`。
- 新外部输入必须验证。
- 新缺陷修复补回归测试。

### 阶段 3：按触及范围治理

- 修改旧文件时降低复杂度。
- 拆出纯逻辑并补测试。
- 清理循环依赖和万能工具文件。
- 缩小公共 API。

### 阶段 4：专项迁移

- 分模块开启更严格的 TypeScript 选项。
- 按领域迁移目录。
- 引入项目引用和依赖边界检查。
- 清理临时规则禁用和类型断言。

## Ratchet 策略

对无法立即达标的指标采用“只降不升”：

- 文件行数不能继续增长。
- `any` 数量不能增加。
- 循环依赖数量不能增加。
- 被跳过测试数量不能增加。
- Lint 警告基线只能下降。

## 自动生成代码

生成代码可以豁免部分格式、大小和命名规则，但必须：

- 明确标识生成来源。
- 不手工修改。
- 将生成目录排除在不适用检查外。
- 对生成器本身进行测试和审查。

## 大规模重命名

只有在用户明确要求或迁移收益充分时进行。应：

- 单独 PR。
- 不混入功能变化。
- 使用自动化重构工具。
- 检查大小写敏感文件系统和 Git 重命名。
- 验证导入、测试、文档和构建。
