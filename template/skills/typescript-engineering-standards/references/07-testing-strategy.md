# 测试策略

## 测试分层

| 类型 | 目标 | 默认位置 |
|---|---|---|
| 单元测试 | 函数、策略、解析器、状态转换 | 与源码同目录 |
| 集成测试 | 多个真实模块协作 | `tests/integration/` |
| 契约测试 | API、IPC、插件、适配器契约 | 源码旁或 `tests/contracts/` |
| E2E | 用户关键路径 | `tests/e2e/` |
| 基准测试 | 性能关键路径 | `*.bench.ts` |

## 测试命名

测试名描述可观察行为，而不是实现方法：

```ts
describe('quoteShellArgument', () => {
  it('preserves an empty argument as an explicit empty string', () => {
    // ...
  })
})
```

避免 `it('works')`、`describe('utils')`。

## 覆盖范围

关键模块应考虑：

- 正常路径。
- 边界值和空输入。
- 无效输入。
- 错误传播。
- 取消和超时。
- 并发或重复调用。
- 资源清理。
- 已修复缺陷的回归场景。

覆盖率数字不能替代风险导向的场景设计。

## 缺陷修复流程

1. 添加可稳定复现问题的失败测试。
2. 确认测试在修复前失败。
3. 实施最小修复。
4. 确认回归测试和相关测试通过。
5. 必要时增加跨平台或集成测试。

## 确定性

测试不应依赖：

- 真实当前时间。
- 外部不稳定网络。
- 测试执行顺序。
- 共享可变全局状态。
- 本机特定路径或环境配置。
- 无种子的随机数据。

通过注入时钟、随机源、文件系统和网络端口，或使用临时目录与隔离夹具保持确定性。

## Mock 原则

- 优先测试真实纯函数。
- Mock 系统边界，不 Mock 被测模块内部每个调用。
- 测试行为与输出，不锁死实现步骤。
- 不因 Mock 方便而跳过关键集成测试。
- 使用小而可读的夹具。

## 快照

快照适合结构稳定、人工审查有价值的输出。避免巨型快照、频繁无脑更新和对动态数据的快照。

## 测试代码质量

测试也是生产资产：

- 命名清晰。
- 无隐藏共享状态。
- 失败信息可诊断。
- 夹具具有领域含义。
- 清理临时资源。
- 不复制大量生产实现来计算期望值。
