# 项目架构与目录布局

## 先表达边界

目录优先表达以下稳定边界之一：

- 运行环境：`main/`、`renderer/`、`server/`、`worker/`、`cli/`。
- 产品领域：`user-auth/`、`orders/`、`payments/`。
- 架构职责：`domain/`、`application/`、`infrastructure/`。
- 独立发布单元：`apps/`、`packages/`。

不要在同一层混合互不相干的分类逻辑，例如同时出现全局 `components/`、`payments/`、`services/`、`cli/`。

## 领域优先，技术类型局部化

项目很小时可按技术类型组织；业务增长后应将技术目录移动到领域内部。

推荐：

```text
src/
├── app/
├── features/
│   ├── user-auth/
│   │   ├── login-service.ts
│   │   ├── login-service.test.ts
│   │   └── components/
│   └── payments/
├── shared/
└── infrastructure/
```

不推荐长期维持：

```text
src/
├── components/
├── hooks/
├── services/
├── types/
└── utils/
```

## 局部平铺

一个职责明确的领域目录应默认平铺文件，不为每个文件建立同名目录。

建议增加子目录的条件：

- 形成稳定、可命名的子领域。
- 同级实现文件长期超过约 8～12 个，定位成本明显上升。
- 文件组拥有独立入口、资源、测试夹具或生命周期。
- 文件组需要整体移动、替换或发布。
- 依赖方向或运行环境需要物理隔离。

不要创建仅包含一个普通实现文件的目录，也不要为了对称而制造空层级。

## `shared/` 准入

代码进入共享层前应满足：

1. 至少有两个真实调用方。
2. 不依赖具体业务领域。
3. 具有具体、可命名的能力。
4. API 相对稳定。
5. 不会造成反向依赖。
6. 共享确实减少重复，而非提前抽象。

`shared/` 不是“不知道放哪里”的收容区。

## 多运行环境

Electron、全栈、Worker 或混合运行环境项目应物理隔离：

```text
src/
├── main/
├── preload/
├── renderer/
├── shared/
└── types/
```

要求：

- 各环境使用独立 `tsconfig` 或项目引用。
- 浏览器代码不导入 Node 专属模块。
- 服务端代码不无意依赖 DOM。
- 跨环境数据通过显式、可序列化契约。
- 桥接层 API 最小化，并验证来自外部边界的数据。

## 推荐深度

目录深度不是硬性指标，但从领域根目录到普通实现文件通常不应超过三层。深层目录往往表示过度分类、缺少领域命名或每文件一目录。

## 拆分信号

出现以下情况时考虑拆模块或拆包：

- 一个目录同时包含多个运行环境代码。
- 改动一个领域经常触发另一个无关领域。
- 同一目录的文件命名需要大量前缀才能区分。
- 公共入口不断扩大。
- 依赖图出现循环。
- 不同部分需要不同构建、发布或权限策略。
