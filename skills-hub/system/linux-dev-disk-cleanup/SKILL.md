# Linux 开发机磁盘清理

先确认实际主机、发行版、目标文件系统和请求范围。WSL、容器和远程主机的挂载视图与用户设备可能不同。仅审计时不删除、不 prune、不卸载；已有明确清理范围继续有效。

## 建立真实基线

用目标卷的 `df -h` 与 `df -ih` 区分容量和 inode 问题。目录扫描使用 `du -x` 等不跨挂载方式，先定位大目录，再缩小范围，避免重复计算 overlay、loop 或同一文件系统的多个视图。

[平台方法](references/linux-cleanup-workflow.md) 包含 APT、journal、snap、Docker 与语言缓存的具体检查。工具不存在就跳过该分支，不为清理安装另一套环境。

一份简短清单即可保留实际对象、归属、是否可重建、估计大小、处理决定与结果。已有决定不因重新扫描而丢失；大目录不自动成为删除候选。

## 按数据用途选择动作

| 对象 | 主要判断 |
| --- | --- |
| 临时工作目录 | 是否仍有进程或未完成工作，删除边界是否只覆盖指定内容 |
| Docker 容器/镜像/构建缓存 | 当前引用关系、服务状态与重新构建成本 |
| Docker volume / bind mount | 业务数据用途；“unused/dangling”不能证明里面没有需要的数据 |
| 语言与依赖缓存 | 工具支持的清理方式、离线重建与后续下载代价 |
| APT / snap / 内核 | 预览实际移除范围，保留当前与可用回退内核 |
| journal / 日志 | 排错与保留需求，清理已有日志和修改长期上限分别判断 |

优先工具自身的清理/卸载命令。Docker 只处理批准范围，不用 `docker system prune -a --volumes` 代替逐对象判断；具体删除和 prune 的范围按本次数据用途选择，不套固定顺序。

`apt autoremove` 先预览；snap 的旧修订核对 disabled 状态并使用具体 `--revision`。journal vacuum 与长期上限按请求处理，不默认改服务配置。

## 执行与验证

删除前核对对象身份、路径和当前占用。保留源码、业务数据、凭据和活动工具链，不从家目录递归查删 `dist`、`build`、`node_modules`。不删除 `/tmp`、`/var/tmp` 本身或 `systemd-private-*`。

路径包含未点名内容、现场与清单不符、保留依赖可能被删除或权限不足时，停止受影响项并保留其他已授权工作。

分批测量目标文件系统的实际可用空间变化，核对相关容器、项目与保留工具。目录估算不能相加冒充释放量；删除后的内容未必可恢复，记录应如实说明。

交付已处理对象、实测收益、失败与保留原因。小清理不需要额外流程状态，长期经验只提炼会帮助未来判断的内容。
