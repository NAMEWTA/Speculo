# Linux 开发机清理方法

按用户目标定位实际占用和可回收对象。大范围清理可以用一份简短记录保留基线、选定对象、保留项和结果；小范围清理无需先填写固定表格。已经给出的范围和授权持续有效。

## 找到真正占用的文件系统

```bash
df -h
df -i
du -xh --max-depth=1 /path/to/suspected-directory
```

先确认空间不足发生在哪个挂载点，再向大目录下钻。overlay、bind mount 和同一文件系统的不同视图不能重复相加；ISO 挂载的容量也不等于宿主分区占用。不要固定只看根分区，开发数据可能在独立卷。

inode 紧张时重点找大量小文件；`du` 与 `df` 差距明显时考虑打开但已删除的文件、快照、保留空间和挂载遮蔽。有 `lsof` 时可按目标进程/挂载检查删除文件，不能为释放空间盲目杀进程。扫描优先限制在有证据的目录，避免遍历同一容器层多次。

按任务读取 `journalctl --disk-usage`、`docker system df`、包缓存、项目构建目录和用户缓存。用 `go env GOCACHE GOMODCACHE`、`npm config get cache` 等定位真实位置，不假定所有用户都使用默认路径。

## 判断能否移除

| 对象 | 方法与边界 |
| --- | --- |
| 临时工作目录 | 核实实际路径、所属任务和进程占用；旧 mtime 本身不能证明已废弃 |
| 项目构建产物 | 优先使用项目工具，例如在对应 Cargo 项目执行 `cargo clean`；保留源码与本地状态 |
| 可重建缓存 | 说明重建成本与离线影响，区分构建缓存、依赖缓存和已安装工具 |
| 包与旧修订 | 用包管理器识别归属；保留当前运行内核及仍需要的回退版本 |
| 日志 | 先考虑排障和保留要求，再按容量或时间清理；不自动设统一上限 |
| 容器数据 | 区分镜像、构建缓存、容器、volume 与 bind mount；无引用不等于无价值 |
| 用户或业务资料 | 仅按已明确的具体范围处理，不把它归入通用缓存 |

删除前检查目录是否经符号链接或挂载解析到其他位置。父目录包含未识别或需保留子树时只处理已确定对象，不扩大到父目录。不要从家目录或仓库根递归扫删所有 `build`、`dist`、`node_modules`。

## Docker 与服务数据

先读取当前 context、`docker info` 的数据根、容器状态及 Mounts。停止的容器、未挂载 volume 也可能保存数据库或离线环境；运行中的服务常用宿主 bind mount，这些不包含在 volume 列表里。

按用户选定的对象使用 `docker rm`、`docker image rm` 或 `docker volume rm`。使用 prune 前核对本机版本的对象范围、过滤条件和引用关系；`docker system df` 的 RECLAIMABLE 只是技术上的可回收量，不是业务可删除量。不要因剩余超过某个容量就自动升级到 `-a` 或 `--volumes`。

需要删除容器时先明确它的数据如何保留，避免移除最后一个引用后把 volume 也当作垃圾。只清 build cache 时不附带删除镜像、容器或业务数据。清理后确认需保留的容器、挂载和代表性服务仍正常，不能只核对 volume 名称还在。

## 开发工具与包缓存

在实际用户和项目范围使用工具提供的命令。常见区分：

- `go clean -cache` 清构建缓存，`go clean -modcache` 还会移除模块缓存，后者需要重新获取依赖。
- `cargo clean` 针对项目构建结果；Cargo 的 registry、git 缓存与 `bin` 工具目录分别判断。
- `npm cache clean --force` 不是清空整个 npm 用户目录的授权；`_npx` 等其他内容单独核对。
- `pnpm store prune` 按工具规则处理 store，不保证释放指定容量；活动项目与离线使用会影响取舍。
- Maven `repository` 中可能有未发布的本地安装包；保留 `.m2/settings.xml`。Gradle cache、wrapper 分发与安装配置也要区分。

系统包清理使用该发行版的包管理器。例如 apt 的 `clean` 清下载缓存，`autoremove --purge --dry-run` 展示依赖移除范围，二者效果不同。核对实际拟删除项后再执行，不能把 dry-run 通过视为业务无风险。

snap 用 `snap list --all` 核对具体修订；删除旧修订时使用 `snap remove NAME --revision=REV`，避免变成卸载整个应用。日志清理如 `journalctl --vacuum-size=` 应使用适合本机的目标；持久上限是另一个配置改变，按需要决定。

## 完成与异常

在相同挂载点测量真实空间和 inode 变化。目录大小总和不等于释放量；活跃系统数据持续变化，也不能仅凭大小没变证明业务完整。

按影响检查保留项目、工具版本/路径、容器健康或代表性业务。清理遇到权限、占用或目标不明时保留该项并报告原因；无需停止全部独立工作。

记录删除了什么、实际收益、未处理对象及后续成本。删除数据不能凭一个“回滚”标题恢复；可再下载缓存也需要可用网络、来源和版本。

## 历史案例的用法

原技能的 Ubuntu 案例里，主要空间来自已结束的临时工作目录、构建缓存和未使用容器数据；一个含未确认子树的项目目录被保留。它说明应逐对象判断，不提供可在其他机器重放的路径清单或预期收益。
