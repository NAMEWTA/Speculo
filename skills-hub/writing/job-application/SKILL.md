# 岗位投递与面试准备

经历原件是可复用资产，每次投递是面向岗位的表达。先理解用户这次需要哪种材料、目标岗位和可用经历，直接完成已清楚的部分；只要自我介绍时，不先强制制作整套投递包。

## 从哪里开始

| 已有材料或请求 | 当前工作 |
| --- | --- |
| 只有简历、笔记或知识库 | 按 [经历提纯](references/experience.md) 找出可复用事实、个人贡献和证据缺口 |
| 有 JD 与经历 | 按 [岗位与公司研究](references/targeting.md) 匹配要求，再写目标材料 |
| 只给岗位名称 | 可以先形成明确标注的岗位假设；需要该公司的具体要求时查官方岗位或请用户补充 |
| 改简历或换一种表达 | 按 [简历写作](references/resume.md) 调整选择、顺序和措辞，保持事实一致 |
| 口播、预测题或模拟面试 | 按 [面试准备](references/interview.md) 绑定真实项目、决策和缺口 |
| 想知道怎样补短板 | 按 [提升计划](references/development.md) 区分表达问题、证据不足和实际能力差距 |
| 要完整投递包 | 按岗位需要组合上述工作，共用经历依据，核对各份材料的一致性 |

复用已有用户偏好、工作区和原始材料。只有会改变产出方向的缺口才询问，例如目标岗位、实际承担的职责或互相矛盾的数字。公开公司信息可以解释岗位环境，不能变成用户个人成就。

## 事实与表达

每条重要经历能回到用户资料、原始记录或用户的明确确认。区分事实、用户给出的估计、自己的解释和表达选择；估计保留“约”等限定。

学历、任职时间、公司、正式职级、署名、仓库所有权和个人贡献范围保持真实。协作项目要写清自己负责什么；学过、试用过与生产使用过分开表达。缺少数字就用具体的定性结果，不编造提升百分比。

JD 有而经历没有的内容进入缺口分析，不塞进技能栏。原件中的冲突回到来源核对，不自动采用更好看的说法。调整措辞或翻译可以改变表述角度，不能把内部小工具升级为平台级经历。

## 工具与格式

知识库只读指定范围，先搜索相关主题再回读原文。大库可用 [索引与渲染工具](references/tools.md) 建立可重建索引；索引摘要不是完整证据，二进制索引也不等于已读文档。

`render_resume.py` 和 `resume.css` 可生成 HTML，并在依赖可用时生成 DOCX/PDF。按真实需要选择工具，检查导出后的换页、文字提取和可读性；缺依赖时交付实际可用格式，说明哪个导出尚未完成。

默认使用易读的单栏与常规章节，保留用户已经选择的版式。压缩内容优先于缩小字号；页数、照片与语言依据岗位和用户要求决定。

## 保存与交付

单次文字草稿可以直接在对话交付。需要长期复用或文件时，在用户指定或已有工作区维护一份经历笔记，保存事实、来源和补证事项；每个岗位保存 JD 来源、实际交付文件及重要取舍。较大的经历库再拆分，不先建立十九节空档案或双写配置。

源知识库与技能包保持原样。岗位材料不要反向污染经历原件；新事实经核对后更新原件，后续投递再复用。重要来源可用自然语言或链接关联，不要求 claim ID 和行尾注释。

交付用户请求的材料、主要选取理由、未解决的事实与实际渲染结果。写完投递材料不表示已经向公司发送。
