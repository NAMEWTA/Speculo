# 仓库整理的判断方法

先确认“整理”指盘点、提出建议还是执行指定动作。复用用户已作出的选择，不把每次执行都退回一次新的审批清单。

## 评估用途与独特价值

调查仓库是否仍被部署、包、文档、Pages 或其他仓库引用；是否有本地独特提交、开放 PR、issue 中的决定、release 附件或需要保留的历史。fork 应比较上游与自己的改动，不能只看仓库类型。

最近推送、stars、CI 和开放问题是证据的一部分。长期没有 push 可能是稳定发布，CI 失败可能只是过时依赖；这些都不是直接删除依据。空仓也可能保留地址或等待迁移。

建议应指向具体问题，例如迁移后旧地址的使用者如何找到新仓，归档前是否需要最后一版说明，重复 fork 是否有未移交内容。保留、归档、删除、迁移和取消星标分别说明影响。

## 推进已确定的动作

输出具名对象、事实依据和相应动作即可，形式按数量选择。若用户只要求建议，到建议结束；若用户已要求处理这些对象，准备依赖后执行，不增设通用“等待点名”步骤。

执行顺序由依赖决定：先保存独特资料、调整链接或迁移使用者，再关闭旧入口。星标调整通常独立于仓库生命周期，不必固定放在最后。遇到对象不匹配或独特数据未处理，只暂停受影响项。

## 验证结果

逐项读回归档、删除或星标状态，必要时确认链接和保留仓库可用。报告真正完成的动作、失败及尚需处理的依赖。无需为了格式再生成一份与现有结果重复的固定总表。
