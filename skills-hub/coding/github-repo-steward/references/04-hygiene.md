# 仓库卫生方法

先盘点，再出**建议清单**，等用户点具名仓。不要自行扩大范围。

## 建议规则

1. **原创 + 近 60 天有 push** → 保留。
2. **原创 + 长期无 push + 有 star 或有文档** → 建议归档，不删。
3. **Fork，且自己已用新仓替代**（例如旧 RuoYi fork 已迁到自己的 monorepo）→ 建议删除。
4. **Fork，仅作上游跟踪、自己无独特提交** → 问用户：留着同步 / 删除。
5. **空仓、错 fork、一次性实验** → 建议删除。
6. **已归档** → 除非用户要灭迹，否则不动。
7. **CI 失败** 只报告，不当作删除理由。
8. **开放 PR 很多** 只报告积压，不当作删除理由。

## 建议清单格式

```
归档（可逆）
- OWNER/REPO — 原因

删除（不可逆）
- OWNER/REPO — 原因

保留
- OWNER/REPO — 原因

取消 star（与自有仓无关）
- OWNER/REPO — 原因
```

用户回复「按这份做」或点名子集后，再进入 archive / delete / stars-mutate。

## 执行顺序

1. 归档（失败也不影响删除）
2. 删除
3. unstar（独立权限，可单独做）
4. 逐项 API 复核
5. 再跑一次 `gh repo list` / star 列表，把新状态表给用户
