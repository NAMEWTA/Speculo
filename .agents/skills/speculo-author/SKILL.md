# 维护 Speculo 的工作方法

Speculo 把专业方法交给模型，并把可复用知识留给下一次工作。先弄清楚用户希望保留的能力，再决定它需要几个入口和文件。

## 按改动选择指南

| 改动 | 读取 |
| --- | --- |
| 调整领域边界、完整工作链、领域路由或跨 Work 关系 | [Workflow](references/workflows.md) |
| 新建或改写一个可独立调用的任务方法 | [Work](references/works.md) |
| 改进触发描述、正文、参考材料、工具或 Hub 技能 | [Skill](references/skills.md) |
| 修改一次显式调用的请求、参数、结果或副作用范围 | [Command](references/commands.md) |
| 合并、精简、迁移或删除已有内容 | [保留能力的重构](references/refactoring.md) |

局部事实修正只需读相应源文件；不要把所有指南变成每次任务的预读清单。一个改动可以涉及多个层次，按实际依赖继续读取。

## 从真实来源开始

定位请求对应的入口、实际调用方、资源和测试。分发源在 `template/` 与 `skills-hub/`，CLI 在 `src/`；本目录指导仓库维护，不随用户项目作为运行记录。

领域和 Work 都采用标准 `SKILL.md`。发现、公开 ID、安装与宿主暴露以当前实现为准，参见 [架构说明](../../../docs/architecture.md)。不要为内容新增业务 manifest、自动索引、Canonical 生成层或任务状态 schema。

## 写清楚模型需要知道的部分

交代触发条件、任务特有的方法、容易误判的领域事实、真实工具接口和完成结果。把通用推理交给模型；涉及数据丢失、不可恢复的外部效果或精确工具调用时保留具体边界。

入口承担选择与行动。较长的专业资料、平台差异、示例和参数按需引用，并说明何时读取。精简重复语句和无效流程；保留能改变任务结果的知识、工具与实例，不用文件数或字数判断是否精简成功。

已有用户要求、授权和修正继续有效。需要人决定的产品方向、验收主体或新的高影响范围要明确表达，不添加每个阶段重复确认的通用门禁。

## 持久化与完成

当前事实优先更新原有记录；任务进展与长期知识分开。ADR、context、error、design 是可选归处，原型代码、配置、测试与图片都可以作为知识来源。只保存下一次需要、且不能可靠从现有事实恢复的内容，遵循 [持久化约定](../../../template/references/memory.md)。

验证本次改变的实际行为：内容能否被找到、任务是否能完成、引用是否可用、工具与安装是否仍正常。涉及替换时核对旧能力的去向；涉及安装时保护用户文件。报告实际结果及未验证范围。

改编保留来源和许可证。研究取舍见 [研究依据](../../../docs/research.md)，第三方归属见 [第三方说明](../../../THIRD-PARTY-NOTICES.md)。
