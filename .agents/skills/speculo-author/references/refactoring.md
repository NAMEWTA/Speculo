# 保留能力的重构

精简后的材料应该更容易使用，并继续解决原来有价值的问题。模型能力增强可以减少程序化指挥，不能代替项目私有知识、真实工具接口和经过验证的专业方法。

## 先建立能力映射

读旧入口及它实际引用的资源，查看调用方与典型任务。区分以下几类内容：

- **能力与知识**：例如需求质询、页面结构审查、经历提纯、分页导出、部署数据兼容。
- **确定性工具**：解析器、API 包装、文件转换、安装与事务保护。
- **持续事实**：设计源、环境配置、决策原因、故障证据。
- **表达与控制层**：重复说明、固定模板、任务状态 schema、生成索引、调度协议。

为每个有价值的能力找到重构后的承接位置。可以合并、改写或按需引用，但要能回答“执行这个任务时，模型到哪里获得必要信息”。历史版本存在于 Git 并不等于运行时能力仍可找到。

映射可以用一个简短表格记录旧能力、新入口和验证方式；这是本次重构的评审依据，不是每个用户任务都必须填的表单。

## 决定保留、迁移或删除

保留改变结果的专业方法和反例。将不必每次加载的细节移到可直接找到的参考。重复事实留在最接近真实来源的位置，其他地方链接。

只有确定没有消费者、没有独特能力或已被等效实现承接时才删除。移除协议时一起清理真实调用方和对应测试；不得只删文件、让入口悬空。删除工具前核对它的实际用途，不因扩展名是 `.mjs` 或输出 JSON 就判定它属于过度约束。

例如可以删除“每个 change 必须填写 DESIGN 模板”，同时保留原型、交互状态、设计理由和实现对照方法，并将当前设计源放在长期位置。若只剩“按需做 UI”一句话，设计能力还没有完成承接。

## 重写并保持渐进加载

入口写任务选择和核心方法，参考写需要时才用的知识。不要先定“每份二十行”或“只能一个文件”，再压掉专业内容。也不要把旧目录原样搬进 references，继续要求全量预读。

保留示例中的判断与依据，移除只为固定格式存在的占位项。脚本、许可、源链接与引用路径一并迁移。涉及公开名称或路径变化时检查安装、升级与已有用户选择。

## 用结果验证

选择重构前有代表性的任务，使用同样的必要素材尝试新方法。检查是否仍能得到正确产物、识别同类错误、保留用户要求并从中断继续。记录实际输出或差异，避免只检查新入口是否提到旧能力的名字。

对边界案例做有针对性的补充：设计是代码、输入只有原始记录、外部写入结果未知、已有授权、分支与笔记不一致。审查者只拿到任务与素材时也应能用新入口完成任务。

分别报告静态链接/发现检查、工具测试和任务试用。静态检查通过不等于能力已实测；没有访问真实服务的部分要如实说明。文件减少、行数减少和未量测的 token 节省不作为验收证据。

## 研究方法

优先读原始内容，核对它解决的具体问题。吸收写作原则而非连同上游所有架构一起搬入。参考仓库中可能同时存在精简原则和复杂编排，需逐项判断。

本仓库的来源及取舍见 [研究依据](../../../../docs/research.md)。原创综合、改编文字和复制工具分别注明归属，保留许可证，避免把未经验证的推断写成权威规范。
