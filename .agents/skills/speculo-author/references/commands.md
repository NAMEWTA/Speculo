# 编写 Command：把一次明确请求做完

Command 表达用户显式发起的一次操作，例如交接任务、分析 Git 变化或审查一份产物。它应让调用范围和完成结果明确，复用现有方法，不承载另一套工作流调度系统。

## 定义一次调用

说明用户要解决的问题、可用输入和输出位置。参数有默认值时应来自当前上下文或工具真实行为；缺失的信息能从文件和环境获取，就先查证。

区分查询、生成本地产物与修改外部状态。用户已经明确要求的动作不再增加通用确认环节；确实缺少范围或新出现不可逆效果时，先把能完成的准备做完，再提出具体问题。

例如“为当前改动提 PR”包含检查差异、补足描述和创建 PR；不包含合并到生产或发布包。仅要求“分析部署风险”也不意味着已经请求执行部署。

## 入口与复用

命令源放在 `template/commands/<name>/COMMAND.md`。当前发现实现使用 `id` 与 `description`，其中 `id` 与目录一致；Command 不是额外的标准 Skill 源。宿主包装与暴露由 CLI 负责，不手工维护多份拷贝。

正文可直接说明目标与方法，或链接已有 Work/参考。用当前包结构能解析的相对链接，不创建不存在的 slash command、工具参数或模型调用 API。

如果方法会在多种请求中使用，把专业细节放到合适的 Work/Skill，并在命令中说明何时调用。避免复制正文后两边分别修改。无需为一次调用增加 task state、派单目录或单独的 JSON 报告。

## 记录与恢复

结果优先更新任务已有的记录。需要新报告时用清晰且不覆盖无关资料的路径；不必为每次轻微操作留下永久文件。

远端写入遇到响应不确定时，先按对象身份读回实际状态。重试之前确认上次是否生效，避免重复建 issue、重复部署或重复发送。部分失败时说明完成和未完成的实际边界，继续处理独立且仍在授权内的部分。

## 验证

检查命令能被发现，生成的宿主入口指向真实资源，参数和引用可用。用一次有代表性的请求检查输出是否满足用户，而非只验证包装文件存在。

涉及 Git、远程 API、发布或部署时，验证现有授权的作用范围、目标身份、写入结果与失败恢复。不要把这些类别一概转化为“每次执行前再问一次”。
