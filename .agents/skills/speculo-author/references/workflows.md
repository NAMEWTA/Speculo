# 编写 Workflow：组织完整工作链

Workflow 是一个领域的入口和方法集合。它帮助模型找到当前需要的工作，不负责调度代理、维护业务状态机或要求用户逐步过关。

## 先确定领域边界

从真实请求识别共同对象、长期知识和完成结果。例如 SpecDev 的需求、UI、实现与部署围绕同一次软件交付；部署读取相同的版本和验收事实，因此适合放在同一领域。学习一个知识点与维护软件发布的目标和资料不同，可以各有入口。

列出领域已有能力及其消费者，再判断合并是否减少重复背景。名称相近不代表可以删除其中一个方法；同一目标下的方法不同，可以共用领域入口、保留独立 Work。

## 领域入口应该回答什么

- 用户现在想做什么，已有材料能支持从哪里开始。
- 哪个 Work 能解决当前问题；触发描述应覆盖常见表达，而非只列内部编号。
- 哪些资料共享，哪些结果要交给后续任务，以及它们的真实位置。
- 领域有什么会影响判断的连续性，例如已决定的需求、确认过的 UI、当前发布版本和环境。

说明常见路线即可，不把路线变成必经顺序。用户可以只整理需求、直接修 bug、已有 spec 后开始实施，或复用环境记录部署。是否做原型、拆分 spec 和切片，应由任务规模和不确定性决定。

## 组织文件和引用

领域入口放在 `template/workflows/<domain>/SKILL.md`，可独立调用的 Work 放在其直接子目录的 `SKILL.md`。名字与目录一致，使用标准 `name` 和 `description`；发现实现不依赖额外注册文件。

在领域入口链接 Work 并用短句区分适用场景。共享知识只有确实被多个任务复用时才单独保存；不要为了统一目录给每个 Work 新建空的 rules、schemas、assets 或 references。

用户项目中的需求、设计与环境是运行资料，不写进分发源或技能目录。引用现存资料即可；无需为让领域索引“完整”而复制 spec、原型或执行记录。

## 处理交接和失败

把交接写成需要接续的事实：已确定什么、有哪些实际产物、尚缺什么、下一步从哪里继续。失败只影响依赖该结果的工作；独立且已授权的部分仍可继续。中断恢复先核对文件和外部状态，不能只相信上次笔记的“完成”。

人明确要求的设计评审、验收或发布范围随任务保留。缩短流程不意味着可以用自动测试替代指定的人做决定。

## 检查改动

用真实任务走读入口：首次进入、已有部分资料、从中间开始、跨会话恢复、一个依赖暂时不可用。看模型是否找到所需的方法与证据，而不是能否背出阶段顺序。

新增或移动 Work 后验证发现、选择安装、宿主暴露、相对引用与公开 ID 的连续性；涉及升级时核对旧路径与用户修改的处理。不要仅靠索引条数或章节齐全判定工作流可用。
