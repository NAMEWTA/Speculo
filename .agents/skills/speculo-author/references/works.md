# 编写 Work：保留可独立完成的任务方法

Work 是用户可以单独调用的一项领域能力，例如评估需求、设计原型、审查实现或部署到已知环境。它有可判断的结果，但不必对应一个强制阶段。

## 从请求和产物倒推方法

选择有代表性的请求，确认用户给了什么、还缺什么，以及怎样判断任务完成。先查代码、文档、原型或环境能否补足缺口；只有确实影响方向且无法推断的问题才问用户。

描述任务中需要专业判断的环节。例如原型设计要识别用户路径、信息结构和空白/错误等状态；代码审查要追踪影响与失败条件；部署要核对目标环境、版本、数据兼容及恢复方式。这些方法不能只缩成“分析并交付高质量结果”。

把输出写成实际可用的东西：设计源、代码差异、发现及证据、可执行部署或简短结论。用户只要小修时不要制造一套完整交付文档。

## 决定正文与参考的边界

将任务目的、关键判断、必要边界和完成判据留在入口。分支很多时，用直接链接指向相应方法、示例或工具，写明触发条件。模型应能从入口找到全部必要能力，无需遍历整个领域。

示例展示容易误解的判断。参考保存具体专业知识。脚本负责确定性的操作。不要把正文搬到引用后只留下抽象口号，也不要把输入、输出和检查在多个文件重复定义。

## 与其他 Work 连续工作

复用上游的事实和来源链接，而非要求上游先把材料抄入固定表格。产物已有稳定位置就直接引用。需要独立 spec、任务切片或交接文档时再拆，保持每份内容有明确用途。

允许直接调用、跳过无关环节和返回修正。若发现需求与实现不一致，说明差异并按已有目标处理；不要靠写入某个 status 字段让问题“流转”到下一阶段。

归档保存当时结果；长期知识提纯有效的原因、环境方法、故障经验或设计源。用户已认可的原型可以是代码，不强制在 change 内复制 `DESIGN.md`。

## 实际验证

选择能暴露本次修改风险的情境：输入不完整、已有设计直接实施、旧交接与当前代码冲突、工具部分失败等。检查输出能否被后续使用，是否诚实保留未完成项，是否错误扩张授权。

若修改工具或真实外部接口，验证参数、失败与读回。若只改写方法，用任务结果审查语义与可用性，不新增只检查标题或关键词的测试。

文件放在 `template/workflows/<domain>/<work-name>/SKILL.md`。公开 ID 和安装行为由当前发现实现派生；改名时一起检查调用方、用户选择和升级行为，避免只改一个入口。
