# 编写 Skill：把专业能力放到正确上下文

## 触发与职责

描述用户什么时候需要这个能力，以及它能做什么。把容易混淆的边界写入 description，例如图片编辑与从零生成、配置优化与代码故障分析、意图整理与正式需求评估。正文在触发后才读取，不要依靠正文修补完全不准确的触发描述。

先检查现有技能能否直接承接。相同任务的不同平台通常适合共用入口、按需读取平台参考；目标不同且能独立使用的能力可以保留独立技能。不要因为都“与写作有关”就把教学、简历和技术表达合并为无差别入口。

## 保留能改变结果的知识

检查每段内容的作用：提供工具不易发现的限制、区分相似概念、说明专业判断、保留反例或让模型恢复真实状态。删除重复口号、一般性常识、无效流程要求与已经过时的接口。

具体方法可以很短，但不能只说“先分析、再执行、最后验证”。例如求职材料需要区分团队结果与个人贡献；API 技能需要说明分页、对象身份与不确定写入的读回；磁盘清理需要区分可再生缓存和唯一数据。

允许模型选择实现路线。只对真实脆弱部分给精确要求，例如工具参数位置、文件编码、数据库一致性、不可重复的外部动作。来源材料中的固定轮次、角色分配或表格不自动成为本技能的约束。

## 按需资源

| 内容 | 适合的位置 |
| --- | --- |
| 每次都需要的选择与行动方法 | `SKILL.md` |
| 只在某个平台、任务分支或疑难情境需要的知识 | `references/` |
| 确定性的重复操作、解析器、真实 API 包装 | `scripts/` |
| 最终产物使用的样式、图形、示例源或原型 | `assets/` 或现有对应目录 |

只有实际需要才建目录。从入口直接链接重要参考并说明用途。安装后路径应仍成立；区分技能目录的资源路径与用户项目中的产物路径。

工具的 JSON 输入、锁文件、事务记录和解析器可能有真实用途。删除的是让模型为了服从流程而维护的冗余状态，不是所有结构化数据。脚本应有可查的调用示例、依赖、错误语义和适用平台。

## 来源与边界

优先核对官方接口和原始资料。改编保留来源、许可证及真正引用的范围；不要把一次第三方测量写成通用结论。标明原作者方法、当前项目取舍和未核实之处，避免冒称与上游完全等价。

更新已有 `agents/openai.yaml` 时让展示描述与技能一致，不为了形式添加宿主不使用的字段。标准格式和分发约束由当前工具校验；不引入自定义业务 schema。

## 行为评估

用贴近实际的请求检查触发、选择参考、操作和最终结果。独立试用只给任务和必要素材，避免先告诉执行者预期答案。保留实际产物、差异或日志作为证据。

检查典型路径与此次改动容易损坏的边界即可。没有运行工具或外部服务时明确说明，不把文本走读称为端到端测试。词数、文件数、关键词出现率只能描述结构，不能证明专业能力或质量。
